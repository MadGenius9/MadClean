# Disposable Windows validation harness

`MadClean.WindowsSmoke` is a development/CI executable, separate from MadClean's production UI and providers. It requires Windows with the .NET/WPF runtime and an explicit opt-in. Run **only in a disposable Windows runner/VM**, from the existing repository root. It is not a personal-PC inventory tool or a servicing/repair test.

```powershell
$env:MADCLEAN_WINDOWS_VALIDATION = '1'
dotnet run --project tools/MadClean.WindowsSmoke -c Release --no-build
```

The coordinator adds the project to the solution/build and locked restore workflow. This document does not imply that Windows execution has occurred. Linux can cross-compile it; Linux cannot execute WPF or pass this Windows gate.

## What it does

1. Loads the real production `App` with an assembly-qualified `StartupUri`, lets WPF create its single startup `MainWindow`, waits until application-idle before inspecting it, and uses software WPF rendering inside this process. It injects no sample values, clicks no update actions and starts no maintenance. Initial captures/navigation run before any inventory command; the explicitly bounded metadata/search interactions below run only after the final capture.
2. Requests actual WPF **client content** at 1420×1000 and 980×650 window sizes, verifies observed bounds, and keeps constrained captures inconclusive. Its sizing helper changes only the already shown window’s own maximum tracking bounds/size, never global display settings. The modified native limits are passed to WPF’s original handler so its layout cache observes the same actual bounds; a successful API return alone cannot pass the wide check. It checks the primary controls' visible bounds, exercises actual primary/More tools selection bindings, opens the real tool popup, visits all secondary pages and captures H1/new module pages. It asserts navigation generated no inventory activity. Physical keyboard/screen-reader behavior, true OS-DPI scaling, native DWM/title-bar composition and visual fidelity still need separate checks.
3. After every capture and unchecked-navigation assertion, explicitly invokes the existing desktop registration refresh through the UI command and tests actual bound search/Clear/grid selection, unchanged full source/baseline and no extra activity from filtering. A separate required `ui-packaged-app-search` then invokes the existing current-user package read command and tests its actual loaded collection, bound Name/Publisher filter, exact grid selection/details, hidden-selection reset and Clear. Desktop rows/baseline/status remain unchanged by package reading. Missing usable real rows, unavailable metadata or timeout stays inconclusive. Queries are read-only metadata; no fixture rows enter the UI. Reports export only counts/fixed flags, never names/publishers/identities/versions/search text/details. **No screenshot follows either metadata interaction.** Physical keyboard/accessibility and every provider-policy variant remain unverified. After closing WPF, clears the closed dispatcher synchronization context and creates a uniquely named, ownership-marked fixture tree under repository `artifacts/windows-validation-fixtures-<GUID>`. Fixture files are intentionally test data; they are never injected into the production UI.
4. Uses the public duplicate adapter on independent equal-content files, a different file with the same size, and (where supported) a real native hard-link alias. Checks content/identity relationships without a reclaimable-space or safe-delete claim.
   The separate required `duplicate-pair-review-fixture` reuses that same real owned snapshot. Typed independent entries must produce a documentary pair preview with disabled execution; actual aliases, same identity, cloned selections and expired observations must not. Pre-cancellation must be observed. No second scan, fixture UI data, file action or current-keeper protection is claimed. The initial production pair worksheet is captured separately as `tool-22.png`, with both actual list selections empty and commands disabled, before any populated UI data.
   Separately, `disk-identity-fixture` creates a real `DiskUsageScanner` map of three independent equal-size files (two have equal content) and an actual hard-link alias. It checks the public native identity adapter returns four path observations, three independent identities, correct alias/link counts and distinct path/unique logical totals. A fixture-only byte audit checks unchanged contents; the accounting adapter itself is metadata-only. Reports export no paths, file IDs or contents. Failed hard-link setup or incomplete native coverage stays inconclusive; no allocation/reclaimable-space/content-deduplication claim follows.
5. Creates two local `.lnk` fixtures through system Windows Script Host COM **for development setup only**, targeting a fixture text file and an absent fixture path. It never launches or resolves links, creates network-target fixtures or activates installers. Production S1 remains read-only. It tests expected local availability states and records unsupported/access/metadata uncertainty explicitly.
   After the existing unchanged-fixture assertion, `shortcut-selected-recheck-fixture` reuses the same real snapshot and exact missing-row reference. It reads only that `.lnk`, creates its previously absent owned test target with CreateNew to simulate an external restoration, then directly rereads the same scope. No folder rescan or read retries mask completion/gate behavior. Historical rows and link bytes must remain unchanged; the explicitly created target is left for normal owned teardown. Reports export fixed states/flags only. Genuine tool23 captures the empty disabled recheck panel before all populated UI reads; no fixture data enters that UI.
6. Explicitly queries the disposable runner's Application/System event **metadata** for one day. It checks window/channel/recurrence/source-uncertainty invariants. It does not collect event messages/properties, raw report contents, Security logs, dumps or repair output, and no-event results are never health verdicts.
   The same already-read report is passed to the portable recurrence summary; state/window/record and repeated-group counts must remain consistent. No second query or event/WER incident correlation is performed.
   Separately, `defender-status-contract` invokes the existing fixed read-only Defender status/history getters, under their 45-second process budget. At least one nonnull status flag is required to verify a real projected result; Partial status/history coverage stays explicit. Missing/denied/failed/unsupported/no-known-flags results are inconclusive. Evidence contains only fixed state/counts/schema booleans, never actual protection/settings values, mode, signature versions/dates, detection IDs/times/paths or provider messages. Empty detection history is not a clean-PC verdict. No malware scan, remediation, preference change, signature update or elevation is requested. Semantics were checked against current official Microsoft [Get-MpComputerStatus](https://learn.microsoft.com/powershell/module/defender/get-mpcomputerstatus) and [Get-MpThreatDetection](https://learn.microsoft.com/powershell/module/defender/get-mpthreatdetection) documentation.
   `installed-registration-contract` separately requests actual read-only CI-host Add/Remove Programs metadata. A real nonempty bounded response is required for its narrow metadata proof; Partial results never establish a complete baseline. It checks fixed source-bound unique identities, normalized-or-unknown paths, typed restriction/mechanism evidence and UTC observation bounds in memory only, plus pre-cancellation and the pending-worker gate. No app names, registration/product IDs, paths, times, flag values, raw uninstall commands or provider text enter the report. Empty/unknown/unavailable or still-pending reads are inconclusive. It writes no registrations, prepares no action plan, launches no handoff and uninstalls nothing.
   `msi-registration-contract` reuses that validated in-memory result and checks at most three exact selected MSI products in source-matching current-user/machine contexts. Pass requires a real unique Installed context and exact known display-metadata match, with provenance, restrictions, Partial coverage, timestamps, pre-cancellation and worker ownership retained. Missing/advertised/ambiguous/mismatched/unavailable metadata stays inconclusive. No SID values, product/context identities, names, versions or provider messages are exported; no fixture MSI is registered/installed/repaired/uninstalled. The separate UI stage captures the genuinely scrolled unchecked MSI panel as `tool-20.png`, checks its disabled bound command/empty production collection and starts no query. This image is a nested existing page, not a new navigation route or sample mode.
   `bounded-registration-fixture` seeds fewer than 64 KiB of inert metadata in its own marker-protected `HKCU\Software\MadClean.WindowsSmoke\<fixture GUID>\BoundedMetadata` subtree. It checks native fixed-cap text/flag reads, strict malformed-byte rejection, literal expansion-string preservation, missing values, maximum-length subkey enumeration/end, cancellation and presence-only API separation. It never changes actual ARP/startup registrations. Only fixed booleans/counts/codes are reported; teardown requires the exact ownership marker and expected topology. Presence testing is not instrumentation of native `lpData`: the NULL-data and fixed-allocation claims additionally rely on the separately reviewed helper source.
   The deliberately unterminated seed is independently read into a fixed tiny buffer before assertion: Windows may store its exact terminated counterpart instead. Only exact recognized stored bytes determine expectations; normalized seed data explicitly leaves native unterminated rejection unverified. Portable strict unterminated-byte rejection remains tested; production decoding is unchanged.
7. Separately reads the disposable host’s projected H1 hardware inventory to validate source/property schema and enumeration-completeness metadata. It exports only fixed states/counts/booleans, never actual hardware/identity/property values, and does no manufacturer matching, online-source check or hardware action. A complete PC source is required for this narrow metadata proof; it is not proof of accurate identity or compatible parts.
8. Creates inert test registrations only under ownership-marked `HKCU\Software\MadClean.WindowsSmoke\<same fixture GUID>`, never real startup keys. Verifies read-only inventory/type/byte-count previews, fixture scope rejection, unconditional mutation gates and unchanged bytes/journal/files. Removes only that exact owned registry subtree; this proves no disable/restore, TxR isolation or durable recovery.
9. Verifies the system-tool provider’s immutable execution gate, then submits a dummy acknowledged request that must return before identity, logging, UAC or process creation. It never executes DISM/SFC or enables the gate.
   A separate required `system-tool-identity-contract` explicitly prepares only the genuine DISM and SFC executable identities (fixed CheckHealth/verify-only descriptors, never their commands). Both need positive native trust projections with independent OS path/descriptor/hash/time checks. Missing/revocation/catalog-only evidence stays inconclusive. With the gate checked false, genuine-preview requests must still return Unavailable with no PID/elevation/exit; unexpected enabled state fails without a launch call. Pre-cancelled preparation must stop before querying. Only fixed enum/count flags are exported, not file/certificate values. Normal Windows certificate metadata/cache effects are disclosed. The existing tool16 capture shows the unchecked identity-only summary before all populated data; no identity is injected into the UI.
   Required `system-tool-embedded-version-fixture` separately parses just those two guarded fixed OS files using their held read streams. Both need Matched embedded metadata, bounded resource/name counts, canonical numeric version and preserved caller stream ownership/position. No Prepare/WinTrust/loader/MUI/command is called by this metadata fixture; it cannot establish trusted identity. Nonpositive metadata/access outcomes remain inconclusive. Only parser state/counts are reported; the identity contract separately reports typed embedded diagnostics alongside actual signature outcomes.
10. Removes only its ownership-revalidated fixture tree, refusing reparse ambiguity. No production cleanup/delete/uninstall action is tested. Provider calls have bounded cancellation/deadlines; the entire harness has a four-minute watchdog.

The separately invoked D1b WER probe reads only the disposable host's existing machine queue/archive through `WindowsWerMetadataInventory`, with a 30-day creation-time window. `wer-store-read-contract` verifies fixed sources, UTC bounds, minimized GUID/time observation schema and bounded counts. Report evidence contains only states/counts/booleans and fixed explanations, never the GUIDs, creation dates, coverage text, signatures, keys, report paths or contents. Existing usable metadata verifies only that narrow returned path. Completed accessible empty stores can pass the store-read contract while explicitly recording `populatedMetadataVerified=false`: populated-buffer marshalling, complete history and crash/health conclusions remain unverified. Missing/denied/unsupported/incomplete store reads are inconclusive. No report is created, submitted, archived, deleted or exported; no forced crash, dump read or store policy change occurs. Native calls remain cooperatively cancellable only, under the provider's existing bounded caller wait and single-worker gate.

`wer-v1-managed-layout` independently checks CLR sequential layout against documented 64-bit V1 offsets. It is **not** a native SDK ABI proof. The compile-only [WerAbiAssertions.cpp](MadClean.WindowsSmoke/WerAbiAssertions.cpp) separately asserts the actual installed Windows SDK header layout and store enums. From an **x64 Windows SDK developer command prompt** at the repository root, create an owned `artifacts/windows-validation-abi` folder and compile without linking or executing:

```text
cl /nologo /c /W4 /WX /Fo:artifacts/windows-validation-abi/WerAbiAssertions.obj tools/MadClean.WindowsSmoke/WerAbiAssertions.cpp
```

Record SDK/compiler version and actual command outcome separately. The managed JSON check never claims this optional compile-only command ran. The declarations were checked against Microsoft's current [official SDK WerApi.h](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/WerApi.h), [V1 metadata documentation](https://learn.microsoft.com/windows/win32/api/werapi/ns-werapi-wer_report_metadata_v1) and existing `docs/WER-METADATA.md`. A static assertion passing cannot prove a populated live report response, lifetime races or cancellation inside a synchronous native call.

The hosted-runner entry point discovers the installed latest Visual Studio x64 tools using the standard Installer `vswhere.exe`, initializes that installation's `vcvars64.bat`, and invokes its exact default Hostx64/x64 compiler. It downloads nothing and compiles `/c /W4 /WX` to `artifacts/native-abi/WerAbiAssertions.obj`; that object is not a distributed artifact. Its fixed system-PowerShell wrapper accepts no command input:

```text
python tools/ci_command.py native-abi -- python tools/compile_wer_sdk.py
```

Compiler discovery/configuration/exit failures fail closed. This separately recorded command must actually pass before claiming native installed-SDK ABI proof; it does not change the scope of `wer-v1-managed-layout`.

## Evidence and exit states

Required `shortcut-dacl-fixture` independently audits the same owned shortcut before/after the real selected-file provider read. It compares native identity and aggregate DACL facts, meaningful ACL data and unchanged owned contents without changing any ACL. Private bounded audit buffers are cleared; no SID/ACE data is exported. Passing that normal-source case does not establish null/empty/denied/malformed or cleanup-failure native behavior, effective access or privacy. The installed-SDK compile step separately asserts security-descriptor/ACL layouts and the actual GetSecurityInfo signature; it never queries a file.

The [owned shortcut rename experiments](../docs/SHORTCUT-ACTION-RESEARCH.md) have independent required checks: managed Win32, SDK C++ Win32, and an explicitly selected native NT control on separate fresh owned children. They never retry/promote one another or enable production actions. The native control uses ABI2 and reports immediate/completion NTSTATUS separately from Win32 setup failures. A pending request retains native memory, module and handles beyond the bounded caller wait; uncertain teardown retains the entire fixture and skips subsequent transaction probes. The compile-only SDK check proves the available native type layouts, not an SDK declaration of the dynamically resolved native function. The mapping witness is separate and cannot establish inactivity or safe deletion.

Outputs are fixed beneath `artifacts/windows-validation`:

- `report.json`: `formatVersion:1`, validated `sourceCommit` from `GITHUB_SHA` (or `Unknown`), timestamps, overall `passed`/`state`, individually named checks, and a screenshot filename/dimension/SHA-256 manifest. Details are bounded and contain no raw provider payload, user paths or unique machine/file identifiers.
- `overview-wide.png`, `overview-compact.png`, and `tool-NN.png`: actual client-content renders. Only captures listed with a hash in the **current** report are evidence for that run. A PNG alone, compilation or a source commit does not prove all behavior is verified.

Exit 0 means all implemented scoped checks passed; it does not certify the whole roadmap or personal-PC safety. Exit 1 means a failed check or harness error. Exit 2 means an unavailable/unsupported/incomplete native verification (or no opt-in): **inconclusive is not a pass**. A Partial provider result can still verify a particular fixture relationship when the returned evidence supports it; incomplete coverage remains stated. Failures and provider/access uncertainty remain distinct in the JSON report. The harness never turns a returned PID, empty list, missing artifact or suppressed exception into success.

The final required `startup-transaction-handle-probe` performs two inert rollback/commit tests strictly inside its fresh ownership-marked development HKCU subtree. It uses the documented ordinary-handle/NULL-subkey transaction entry point and verifies actual terminal outcomes before ordinary readback. This is an isolated native mutation fixture, not a read-only operation or a real startup change. No production startup action is enabled. Pending/uncertain transaction or registry teardown retains the entire filesystem fixture tree/marker instead of deleting evidence beneath the worker. See [probe scope, ownership and remaining gates](../docs/STARTUP-TRANSACTION-PROBE.md).

CI should upload the report and captures even on failure. If publishing them to the private verification branch, preserve the report's source commit and screenshot hashes; never publish secrets, raw provider output or a public release as part of this harness.

Roadmap-development validation does not require a distribution ZIP. Keep build, portable tests, compile-only ABI validation where configured, and native/UI evidence enabled on ordinary pushes; leave publish/compress/distribution-upload steps conditional on a separately selected `workflow_dispatch` package input (default false). Development report/test artifact transport is separate from packaging the application for delivery. Do not treat an old executable/ZIP as an artifact of the current validation run.


## Inert process-observation fixture

The required `system-tool-process-observation-fixture` borrows real already-started instances of this same development harness to check exit 0, exit 23, cancellation before/during observation, exit-versus-stop precedence and an unstarted process. Children accept only the fixed private `--inert-process-fixture` mode, fixed case names and exact GUID-owned parent/child markers under this repository's fixture root. Argument dispatch occurs before ordinary output preparation; arbitrary arguments cannot reset screenshots or run queries. No arbitrary executable or command is accepted. Child file signals contain fixed inert data and are guarded against known reparse ancestors.

Stopping observation must leave a live child alive; the parent releases it cooperatively and confirms natural exit before cleanup. The observer never starts, kills or disposes its borrowed Process. Unexpected state or unconfirmed teardown retains process references, held apphost lease and the complete owned fixture tree; a later invocation cannot clear prior uncertainty. Child self-deadlines and parent waits are cooperative: a blocked OS call is not forcibly terminated. This fixture runs no DISM, SFC, servicing, UAC, repair, update or client action. An inert child exit validates only process observation, not Windows health, private result logs, operation recovery or production execution readiness. See [contract and limits](../docs/CLIENT-PROCESS-OBSERVATION.md).


The required `startup-transaction-namespace-observation` runs only after preceding native transaction cleanup is confirmed. Four fresh GUID registry subtrees compare source/ancestor rename and same-path replacement with source-only versus all fresh owned ancestors enlisted. It records first actual outcomes before rollback/timeout, treats1 as Undetermined, never commits interference and requires terminal settlement plus exact teardown. Compact fixed fields retain all four outcomes within the report bound; oversized evidence stays inconclusive. Pending/uncertain workers retain the outer marker/tree. [Contract and official semantics](../docs/STARTUP-TRANSACTION-NAMESPACE.md). No real startup entry, command or production mutation gate is used.


`system-tool-journal-store-fixture` is a separate owned-file prerequisite check after the inert-process fixture. It validates explicit protected current-user/SYSTEM creation ACLs and same-handle readback, fixed inert bytes/flush/reopen, same-process exclusive sharing and refusal of newly owned wrong-ACL/reparse/oversized cases. It removes only its exact validated test link and retains the outer tree on any cleanup uncertainty. No production store, operation history, PID recovery, servicing or elevation is used. [Contract and limits](../docs/SYSTEM-TOOL-JOURNAL-STORE.md).


`system-tool-journal-cross-instance-fixture` runs after the owned store baseline. Its two fixed harness child modes test exact StoreBusy/native32 while the parent holds the record, then an existing-object read after release. Real exit0, exact child audits and final parent identity/length/fixed readback are mandatory. The read child guards ordinary ancestry and a no-delete metadata anchor; CREATE_NEW is still attempted by the factory before OPEN_EXISTING and CreatedIntentFile must be false. Missing prerequisites or nonzero/unknown exits remain inconclusive. No arbitrary command, crash simulation, real operation journal, LocalAppData, UAC or servicing is involved. Cleanup uncertainty retains child/process/store/apphost ownership and the complete marked tree.


`system-tool-journal-lifecycle-fixture` observes only a deliberate fixed child self-exit37 after inert intent flush/readback, then checks reopened Unresolved data, refused prefix changes, exact owned malformed-tail preservation and whole-log Unknown. It skips managed finally on that child only; no real servicing process is launched. Borrowed cursor audits are synchronous, bounded, restored and cleared; uncertainty retains participants/store/tree. [Record and ownership contract](../docs/SYSTEM-TOOL-JOURNAL-RECORDS.md).

`dism-powershell-capability-contract` uses fixed System32 Windows PowerShell with autoload disabled and one inbox manifest import to inspect advertised type/enum/switch metadata only. It invokes no Repair-WindowsImage/DISM/SFC command or output getter, and publisher trust remains unverified. Projection counters distinguish null from actual0; unfamiliar schema stays Unknown. [Metadata scope](../docs/DISM-CAPABILITY.md). Its metadata-process timeout termination must never be reused for servicing operations.
