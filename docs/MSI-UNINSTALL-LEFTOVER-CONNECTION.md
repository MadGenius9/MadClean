# Historical MSI request to leftover review

This source workflow connects the existing actual selected-MSI client result and explicit registration postcheck to the existing read-only leftover candidate review. It does not enable the production MSI launcher, remove files or infer successful/complete uninstallation.

## Evidence and explicit reads

Before an uninstall request, the user must already have captured a **complete covered ARP inventory** through the existing baseline command. Its receipt UTC is retained with that full in-memory baseline. A selected-product lookup or copied MSI row is never promoted to a complete inventory. An absent, late, ambiguous, incomplete or mismatched baseline refuses the connection rather than automatically capturing a replacement.

The later action is available only for the exact historical intent/result and its accepted same-session registration postcheck. The original result and postcheck remain historical; changing the current app-list selection cannot retarget them. The baseline must contain exactly the original selected registration with matching metadata and supported normalized install location. Receipt is an application observation, not an atomic timestamp for all registry entries or a proof of native authenticity.

**Review historical request leftover candidates** explicitly starts a fresh complete covered global registration read after the postcheck. No query starts on client exit, source selection, tab navigation or startup. Incomplete/offline/denied/cancelled reads do not establish global absence. The original manual baseline is not replaced.

The existing comparison engine filters to the historical identity **before** invoking any recorded-path existence probe. It retains the complete prior/current inventories for shared-root cautions. It never sweeps the disk or probes unrelated disappeared registrations. A registration that is present again is not a missing-registration candidate. Repeated or inconsistent source identities block the historical connection.

Returned candidates feed the existing leftover list, initially unselected. A file-level metadata preview still requires its own explicit selection, refreshed registrations, protected/shared-path validation and native metadata checks. No complete-uninstall, exclusive ownership, active-use, junk or removal-eligibility claim follows from client exit, registration absence or path existence. All exit dispositions remain historical observations; no exit code alone grants a leftover or deletion capability.

## Ownership and qualification

The UI retains the actual registration task and underlying native pending work through caller cancellation, display errors and normal close. Late/stale observations cannot publish against a changed historical source or replaced baseline. If ownership cannot be observed, it remains uncertain instead of authorizing another operation or safe closure. Cancellation is not a claim that a registry read was cancelled in Windows.

Portable tests exercise evidence admission and the existing selected comparison with controlled probes. They do not run an MSI, mutate a registry entry, query the user's PC or qualify the WPF/native Windows workflow. Actual current-source owned-product Windows qualification and production MSI gate review remain separate. No Windows execution is authorized by this document.
