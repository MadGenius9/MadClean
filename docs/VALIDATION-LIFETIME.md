# Passive validation observation budgets and worker lifetime

The passive Windows harness has a four-minute **observation budget**, not permission to terminate synchronous native work. Its old watchdog called `Environment.Exit(1)`, which could bypass the identity drain even when actual signature/revocation work remained pending. The new watchdog records the fixed `harness-deadline` failure and saves available evidence without exiting the process. The existing cancellation source still signals the caller's observation deadline.

One portable `ValidationDeadline` serializes timer and final monotonic-clock observations. It records at most one deadline failure, keeps it latched, and prevents a final observer from racing ahead of publication. Main keeps the timer active while the covered owners settle, waits for any in-flight timer callback to finish, then checks actual elapsed time before its final save/exit decision. A delayed callback cannot turn an over-budget run into a pass, and late worker return cannot erase failure.

Main observes actual shared identity-worker admission after both UI and native identity checks. It also retains the exact tasks from the fixed catalog and held-stream catalog fixtures. Their `ValidationWorkerLifetime` objects are installed before the bounded caller waits. Main drains them only after fixture invocation has returned. The worker retains its native resources and owns cleanup; the caller never aborts, force-closes, reopens a PID or performs cleanup underneath it. Fault/cancellation is observed without altering the prior result. A 45-second timeout remains historical Unknown after the worker returns.

The task references cover these three worker families only. They are not a global registration seal or qualification of every legacy passive owner, native cleanup path or application shutdown case. Static roots by themselves do not keep the CLR alive. Other pending-owner families require their own reviewed lifetime work; this increment makes no blanket claim.

The disposable `windows-verification` job still has its existing eighteen-minute outer limit. An expired/hung job is unqualified; VM/job teardown is not reported as native cancellation, cleanup, successful completion or a healthy Windows state. Explicit MSI and non-repair component-store qualification modes retain their separate entrypoints and ownership policies; the passive budget does not wrap them. No SFC execution or repair command is added.

The helper is development-only source in `tools/MadClean.WindowsSmoke`. Portable tests link the same file without WPF or putting it in production Core. Tests cover the exact elapsed boundary, delayed final observation, simultaneous timer/final publication, callback failure, cancelled caller versus actual task, and actual terminal fault/cancellation. Local passes do not establish Windows-native behavior; source-bound Windows regression remains required.
