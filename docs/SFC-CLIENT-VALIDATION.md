# Disposable SFC client-lifecycle qualification

This separate development mode requests only the genuine inbox `sfc.exe /verifyonly` on the disposable GitHub Windows runner. The official Microsoft SFC source read on 2026-11-04 explicitly says this scans protected system-file integrity without repairs; the consulted URL/hash and unsupported exit-code/stop mappings are recorded in [the SFC contract](SFC-VERIFICATION.md). Windows may write CBS/diagnostic metadata. No `/scannow`, repair, offline/custom source, elevation request, installation or restart is permitted. It never runs with ordinary inspection or the passive harness.

The normal application's public execution boundary remains literal false, before platform/privilege/identity/queue/reservation work. The private development entry requires a held exact request proof, fixed hosted CI job/repository/branch/event/source/run/attempt context, a fresh GUID-marked scope under this repository's artifacts directory, and already-effective non-impersonated administrator rights. It is an accidental-use development fence, not cryptographic host attestation or a replacement for Windows permissions. Setting a flag does not change the App's public gate.

The harness first verifies actual fixed executable identity through the existing trusted Windows provider. It prepares a fresh Core preview and explicitly confirmed test intent, preserving the original identity expiry. A separate pre-cancelled intent/proof must return Cancelled without worker transfer, admission reservation, administrator/identity queries by the candidate, or client start. Its setup identity/proof checks are not described as absent. It then prepares another fresh intent and at most one actual client. No retry, alternate executable, mock identity, clock override or parsed provider text is substituted.

Proof ownership transfers after managed owner allocation and shared admission but before worker scheduling. The actual owner retains the original process, both byte-discard tasks, trusted executable leases and marker proof through actual exit/drain/cleanup. Mismatched requests are rejected before queue/native work. Refused transfer releases only unused admission; uncertain transfer/start/cleanup retains the exact proof and blocks cooperating requests. Caller cancellation/timeout does not stop SFC, pipe reads or services. No process is killed.

Stdout/stderr are consumed only by fixed-size raw-byte discard drains; no output text or sensitive values reach CI logs/artifacts. The protected CBS log is only a reference. Actual timestamps and nullable transport observations distinguish unobserved facts from false. The harness keeps the CLR alive through real identity and client/provider pending or retained ownership, including after an invariant exception. There is no local watchdog/forced exit. The thirty-minute disposable job limit is external; expiration is unqualified and not native cancellation or cleanup proof.

The fixed artifact is `MadClean-SFC-client-validation`, containing only `artifacts/sfc-client-validation/report.json`. Its closed version1 schema exports source/run/timestamps, stage/state, boolean lifecycle facts and an actual nullable client exit code. It exports no PID, executable path/hash/version, provider output or arbitrary exception message. Exact source/context, original identity freshness, pre-cancel proof, matching transferred/released candidate proof, actual client start/exit, both completed drains and owned scope cleanup are required. Missing coverage remains inconclusive.

A zero exit is required as this narrow test's normal-client-exit acceptance criterion. It is **not** a documented mapping to successful verification, absence of corruption or whole-PC health. `integrity` must remain `Unknown`, including when lifecycle qualification passes. Nonzero codes remain actual observations with an inconclusive lifecycle outcome. This supplies no scan-result interpretation, timed-stop qualification, public confirmation proof or production activation permission.

The publisher treats this as optional independent evidence: it requires a successful source-matched job/download and strictly valid passed report before setting `sfcClientLifecycleQualified`. Invalid/missing evidence cannot suppress unrelated results; failed/cancelled jobs cannot become qualified. Existing passive inconclusive/failure policy is unchanged. No distribution binary or ZIP is uploaded.
