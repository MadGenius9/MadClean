# Initial foundation review

MadClean starts from an empty repository with a C#/.NET 10 WPF application, a portable core, separate Windows adapters and core boundary tests. It provides a dark eleven-page read-only workspace with user-initiated local inventory, online update discovery, cancellation, per-provider result states and privacy-limited local activity events.

The Windows adapters read fixed disk capacity, two supported temporary-file roots, Run/RunOnce and Startup-folder entries, Defender provider/history data, WinGet list results, and Windows Update software/driver offers. No mutation APIs, fake production data, elevation, installation or reboot operations are included. Limited startup/provider coverage and Unknown/unavailable/partial results are explicit.

Validation: SDK 10.0.403; locked restore; full Release build with zero warnings/errors; **227 core tests passed on Linux (0 failed/skipped)**; locked self-contained Windows x64 publishing passed. A PE32+ GUI executable and ZIP/checksum were produced. Windows UI and live integrations remain unverified and require the disposable-VM matrix in VALIDATION.md. Windows CI is configured but has not run. The branch is committed locally; no push or release is performed.

Review focus: conservative cleanup scope and filesystem races; localized WinGet table compatibility; actual Defender/WUA responses and permissions; Windows GUI/DPI/accessibility; executable signing before distribution. See INTEGRATIONS.md for official documentation and boundaries, and README.md/AGENTS.md for reproducible commands and safety invariants.

The subsequent parallel audits and independent combined review corrected cleanup deduplication/limits, relative-root fallbacks, startup ACL reporting and HKCU duplicate views, partial disk totals, WinGet column/version validation, strict WUA offer metadata/cancellation, and query cleanup after dispatcher shutdown. Defender now resolves built-in modules explicitly; provider executables require absolute known-folder paths. Component ownership remained separate, shared contracts stayed fixed, and the coordinator integrated and validated all changes in this repository. The independent reviewer found no remaining material issue in the final static recheck; Windows runtime limits remain unchanged.

MadClean self-release discovery is now a separate seventh page and Overview status card, disabled by default. An explicit adjacent configuration can enable the pinned GitHub repository; only the dedicated user action checks it. Newer releases produce a timestamped in-app session reminder, bounded plain-text notes and a validated browser review/download action. Private/offline/invalid/cancelled checks remain distinct, preserve an earlier confirmed reminder, and never imply up to date. No credentials, asset downloads, self-installation, scheduler or restart were introduced. A component agent implemented the portable checker/tests and a separate reviewer checked the combined UI/config/network/reminder flow. The full portable suite now passes 227 tests; live GitHub and Windows UI/browser behavior remain unverified.

The discovery extension adds exact cleanup previews with persistent selected exclusions, read-only ARP installed-app/uninstall hints, an original selected-folder logical-byte treemap with linked inspection, and complete-session-baseline leftover candidates. Startup, cleanup and uninstall mutations remain in the visible capability queue, with exact preview/selection gates. The prior phase-one ZIP is retained separately. Official utility documentation was used to benchmark workflows; no competitor code/assets, timing, repair or performance claims were adopted. Three component agents contributed within agreed file/contracts; independent combined review corrected local/reparse ancestry, removal restrictions, settings failure handling, exact-path access and bounded UI viewports. See CAPABILITIES.md and WORKFLOW-BENCHMARK.md.

Windows Diagnostics is added as a later roadmap module only, in the existing capability queue. D1 ships passive evidence and recurring crash/error summaries incrementally; D2 requires explicit non-repair integrity checks with elevation/side effects disclosed; D3 is separately selected guided repair with actual result logs and tool-specific cancellation. Official Microsoft Event Log/WER/DISM/SFC semantics were reviewed. No diagnostic runner, health score, DLL download, automatic repair or inventory hook was added, and no diagnostic/repair command was run.
