# Portable single-driver WUA request-to-job handoff

This candidate connects a managed single-update request to the existing owned WUA job monitor through controlled collaborators. It contains no Windows COM adapter, installer/download/abort call, App command or native execution permission. All existing production action gates remain unchanged. A source-bound driver worksheet, metadata revision, matching hardware string or caller confirmation cannot establish native eligibility, consent, privileges or restart safety.

A request fixes one update GUID/revision and source generation, with one-shot explicit confirmation. A future trusted adapter must separately establish exact fresh native selection, device/OEM eligibility, agreements, dependencies, permissions and supported restart controls before returning a prepared session. GUID/revision metadata cannot establish driver-versus-firmware classification; an actual driver adapter must separately refuse firmware and ambiguous classification. Its actual job/callback graph must already be owned and process-rooted before entering BeginInstall. Managed metadata equality and typed packets are not proof of COM job identity or supported marshalling.

A cooperating **process-rooted** start domain owns the actual prepared session/tasks before invoking collaborators. The job's lifecycle lock reserves that exact start session once across wrappers/domains and shares admission with monitor adoption. Public monitor adoption cannot take a reserved job; a previously adopted job cannot be started. The start domain owns a private monitor domain. These are in-process cooperating-owner rules, not cross-process installer exclusion or a native security boundary. The injected clock supports portable protocol tests; it cannot override any production execution gate or establish native freshness.

Only the exact prepared session/context/job and literal documented S_OK (zero) permit handoff to the monitor. S_OK means asynchronous installation started, never that any update succeeded. Missing/foreign/failed/throwing Begin evidence remains uncertain and retained without retry, EndInstall, cleanup or an inferred no-effect outcome. An early or inline completion does not bypass ownership; the monitor still posts observe/End/read/CleanUp/release on its existing separately rooted workers.

A refusal or cancellation before Begin invocation can report that the collaborator was not entered. It does not claim that native preparation resources were released: those remain the preparing caller's responsibility. Once entry is possible, stopping observation cannot abandon the actual Begin/job task, prove cancellation/rollback, call RequestAbort or release participants. Scheduling or ownership uncertainty stays retained and blocks another attempt. A late result cannot erase sticky uncertainty.

Aggregate and per-update result fields, installed state and actual resource release retain the existing monitor's independent meanings. Even a provider success result cannot establish a working driver, installed version, complete device/OEM suitability or Up to date. No firmware action is introduced.

Portable controlled tests and source review can establish only this handoff protocol. They cannot establish actual WUA Begin failure/output ownership, COM identity/apartments/callback lifetime, cleanup after failed End, exact native collection binding, no-automatic-restart guarantees or Windows permissions/runtime behavior. Those exact remaining questions and official references are recorded in WUA-INSTALLATION-CONTRACT.md. Native implementation and public installation remain blocked on those contracts and qualification.
