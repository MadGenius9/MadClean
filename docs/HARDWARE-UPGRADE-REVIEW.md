# Hardware upgrade prerequisites — planning only

The Hardware Upgrades page has a separate in-memory prerequisite worksheet. Choose RAM, CPU, GPU or storage, enter your own budget, currency, region and use case, then choose **Review prerequisites**. No default preference is inferred from Windows, location or installed components. Budget uses plain digits with an optional decimal point and at most two decimal places; grouping, currency symbols, signs and exponent notation are rejected. Currency/region use supported three-letter currency and two-letter region codes.

The worksheet lists the existing compatibility policy's evidence requirements for the chosen area. Every requirement and the overall compatibility state stay **Unknown**. It has no manufacturer-specification adapter, product candidate, recommendation, price lookup, shopping link, verification checkbox or action capability. Valid preferences cannot satisfy a missing compatibility check. An invalid or absent area cannot yield an empty successful checklist.

RAM review requires exact manufacturer limits/types/population rules, replaceability and physical occupancy. CPU review requires exact supported CPU and BIOS prerequisites, power/cooling and replaceability. GPU review requires expansion wiring/lanes, actual PSU/connectors, clearance and occupancy. Storage review requires protocol/socket, lane sharing, occupancy, mounting and cooling. Exact OEM model/SKU or retail board/independently verified PCB revision is required in every area. Detected facts and family-level service notes cannot satisfy these requirements.

The checklist itself remains generic. A separate explicit [inventory context attachment](HARDWARE-UPGRADE-CONTEXT.md) can display actual already-read PC/baseboard and selected-area observations alongside it; attachment does not match manufacturer specifications or establish that an upgrade is possible. Manufacturer authenticity/content, applicability, conflicting evidence, firmware prerequisites and physical checks remain separate gates. Do not infer soldered-memory upgradeability, PSU capacity, case clearance, spare ports/slots or supported maxima from reported hardware counts or names.

Reviewing, editing and clearing the worksheet starts no query, opens no website, writes no settings/activity entry and changes no hardware or Windows state. Input edits invalidate the old worksheet and attached inventory context before public notifications; **Clear planning inputs** clears the entries. Inputs remain only in the app session. The Core report contains fixed explanations and requirement descriptions, never copies the arbitrary budget/use-case text into its output. There is no persisted/exported plan or approval record.

Portable validation covers malformed/localized/overflow budgets, unsupported or missing areas, bounded preferences, privacy and the inability of complete preferences to produce compatibility. WPF bindings, keyboard interaction, scaling, invalidation and Clear still require a real Windows run. Compilation is not a source-matched Windows result; current runtime evidence must be checked separately. Use the [home-test checklist](HOME-TEST-CHECKLIST.md) for an observational first pass.

## Actual-control qualification candidate

The Windows harness now includes a separate post-capture worksheet interaction. It uses the real area selector, text boxes, Review and Clear buttons, with harmless planning text as user input. It does not substitute hardware/provider data or call inventory, manufacturer, shopping or update controls.

The check covers a blank/missing area, valid memory planning inputs, memory-specific Unknown prerequisites, edit invalidation, GPU PSU/clearance prerequisites remaining Unknown, malformed localized budget input and clearing back to blank. Hardware observations, source context and activity must remain unchanged. It exports fixed outcome flags only, with no preferences, hardware values or loaded-data screenshots.

This qualifies managed form/binding behavior only when its source-matched Windows run passes. It cannot establish physical keyboard/screen-reader behavior, hardware compatibility, product advice, manufacturer evidence, network instrumentation or purchases. Current compilation/source review is not that runtime result. Development is local only as of 2026-11-08; GitHub pushes and Actions are paused at the user's request.
