# D1b — minimized existing WER-store metadata

D1b is a separate, explicit read-only diagnostics source implemented by `WindowsWerMetadataInventory` and the portable `WerMetadataProjection`. It does not start with ordinary Inspect this PC or implicitly with the D1a Event Log query. The application must bind it to its own user-requested action and keep its result/source/time/coverage distinct from Event Log evidence. This implementation has **not been executed against Windows WER stores in the Linux cloud**; portable tests and compilation cannot validate the native APIs or store permissions.

The reader uses documented Windows Error Reporting store functions, not a ReportQueue/ReportArchive directory sweep or an inferred `Report.wer` schema. It never opens dump files, exports raw report contents, starts a reporting process, submits/uploads a report, adds to the queue, archives/deletes/purges reports, enables dumps, changes WER policy or elevates. Windows itself may change stores independently during collection.

## Public result contract

`IWerMetadataInventory.ReadAsync(days, token)` returns `CheckResult<WerMetadataReport>` for an explicit 1-, 7- or 30-day UTC creation-time interval. The report contains `StartUtc`, `EndUtc`, `Observations` and per-source `Coverage`. Each observation exposes only:

| Field | Meaning / limit |
| --- | --- |
| Store | Fixed `E_STORE_MACHINE_QUEUE` or `E_STORE_MACHINE_ARCHIVE` source label; no user/remote/custom store is selected. |
| ReportId | The provider's locally unique report GUID, retained only in the current report. It is not a machine/hardware identifier or proof of a distinct crash. |
| CreatedUtc | Native report creation FILETIME converted to UTC after validation. Creation time is not necessarily the incident/crash time. |
| Category | Literal **Stored WER report**. It is deliberately not a decoded app-authored event label, failure diagnosis, severity or crash category. |
| Source | Fixed `WerStoreQueryReportMetadataV1` plus the store label. No raw key/path/name is included. |

Only nonempty GUIDs and representable positive FILETIMEs are usable. The selected interval is start-inclusive/end-exclusive. Identical repeated references within a store are not added twice; conflicting creation times for a GUID make that reference ambiguous and remove it. A GUID observed in both stores stays source-specific with an explicit warning against adding observations into a distinct-incident/crash total. D1a event record numbers and D1b report GUIDs are different identifiers; do not join them by guesswork or sum both sources as additional crashes.

`StoreStatuses` supplies exactly one typed diagnostic per fixed machine store when projection runs, including Unknown/unavailable reports. It contains only a fixed store enum, state/reason enums, bounded key/metadata/projected-reference/failure counts, a truncation flag and nullable `LastNativeResult`. That numeric result is an actually observed API result, not an inferred Windows error; it can legitimately be `0` (`S_OK`) or the enumeration-end result. The distinct `SuccessfulOpenReturnedNullHandle` and `SuccessfulEnumerationReturnedNullKey` reasons retain **Unknown** with the observed `S_OK`: official documentation promises a retrieved object on successful calls and identifies `ERROR_NO_MORE_FILES` as empty enumeration. It does not document `S_OK` with a null object as empty. No synthetic `E_UNEXPECTED` is presented as though Windows returned it. Missing/ambiguous source responses have explicit diagnostic reasons and no invented native result. Invalid source metadata is rejected, with diagnostic counts reset because they are not trusted. These statuses contain no report IDs, dates, keys, signatures or provider strings, making narrow CI diagnostics possible without exporting inventory.

Empty accessible stores mean no usable references were returned under these source/window/boundary conditions. They do not prove a healthy PC, no crashes, complete history or successful WER submission. Source names alone do not establish the individual report's upload result, cause or impact. No report count becomes a health score or repair recommendation.

## Verified official API and ABI

The following current official Microsoft documentation and SDK declarations were read before implementation:

- [WerStoreOpen](https://learn.microsoft.com/windows/win32/api/werapi/nf-werapi-werstoreopen), [WerStoreGetFirstReportKey](https://learn.microsoft.com/windows/win32/api/werapi/nf-werapi-werstoregetfirstreportkey), [WerStoreGetNextReportKey](https://learn.microsoft.com/windows/win32/api/werapi/nf-werapi-werstoregetnextreportkey) and [WerStoreClose](https://learn.microsoft.com/windows/win32/api/werapi/nf-werapi-werstoreclose): supported existing-store access/enumeration/lifetime. The store APIs are documented for Windows 10 version 1703 and later desktop clients; the application deliberately requires a 64-bit supported Windows build and all required exports.
- [WerStoreQueryReportMetadataV1](https://learn.microsoft.com/windows/win32/api/werapi/nf-werapi-werstorequeryreportmetadatav1) and [WER_REPORT_METADATA_V1](https://learn.microsoft.com/windows/win32/api/werapi/ns-werapi-wer_report_metadata_v1): fixed-size metadata including report ID and creation time.
- [WerFreeString](https://learn.microsoft.com/windows/win32/api/werapi/nf-werapi-werfreestring): every returned enumeration key must be released with this function after use, including early exits. API-owned const key memory is not caller-owned memory to overwrite.
- [WER_REPORT_SIGNATURE](https://learn.microsoft.com/windows/win32/api/werapi/ns-werapi-wer_report_signature) and the authoritative current Microsoft [SDK WerApi.h](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/WerApi.h): actual constants, native declarations, structure layout and store enum values. The official documentation source pages are in [MicrosoftDocs/sdk-api/werapi](https://github.com/MicrosoftDocs/sdk-api/tree/docs/sdk-api-src/content/werapi).
- [WerStoreQueryReportMetadataV2](https://learn.microsoft.com/windows/win32/api/werapi/nf-werapi-werstorequeryreportmetadatav2) and its [V2 structure](https://learn.microsoft.com/windows/win32/api/werapi/ns-werapi-wer_report_metadata_v2) were evaluated but are **not called**. V2 adds report filenames and a filename-buffer allocation protocol unnecessary for this minimal projection. V3 adds still more private application/path fields and is also not used.

The SDK declares `E_STORE_MACHINE_ARCHIVE=2`, `E_STORE_MACHINE_QUEUE=3`. It declares `WerStoreClose` and `WerFreeString` as **VOID**; their interop signatures follow the actual header rather than treating broad prose return-value text as an HRESULT contract. Only `S_OK` produces trusted metadata. Enumeration's documented `ERROR_NO_MORE_FILES` is recognized in direct Win32 and HRESULT-wrapped forms; other return values retain explicit source failures/unavailability rather than becoming empty success.

For the supported 64-bit V1 layout, the header defines 65 WCHARs for EventName and 10 parameter entries, each containing 129 WCHARs for Name plus 260 WCHARs for Value. Signature size is 7,910 bytes; alignment places BucketId at 7,912, ReportId at 7,928, CreationTime at 7,944 and SizeInBytes at 7,952; V1 total size is 7,960 bytes. These declarations were source-verified, not runtime-proven on Windows here. A Windows SDK `sizeof`/`offsetof` compile-time assertion and disposable-runner metadata checks should validate this ABI before a Windows-native readiness claim.

The required fixed native V1 response includes signature parameters that can contain private application information. It would be inaccurate to claim the native API returns no such data. The adapter never decodes/copies those signature fields into managed strings or public results: it copies only the 16 report-GUID bytes and FILETIME, then clears its caller-owned native buffer after each query and before release. Enumeration keys remain opaque native pointers, are never marshalled to managed strings and are freed with `WerFreeString`. No signature, app name/path, raw event label, filename list, bucket hash, Report.wer text or dump payload reaches the UI, export or enum-only activity log. No inventory is persisted by this provider.

## Bounds, access and cancellation

- At most **128 keys per machine store** are inspected for metadata. A further enumerated key detects truncation without querying its metadata. No API ordering guarantee is assumed, so old keys cannot be used as a reason to stop early or to claim that newer matching reports do not exist beyond a bound.
- Metadata is filtered by creation time only after bounded enumeration. The fixed native metadata allocation is 7,960 bytes and public observations are at most 256. Invalid IDs/dates, duplicate/conflicting sources/counts and source failures produce Unknown/Partial results as appropriate; private raw fields are not accepted into the portable contract.
- Loading is restricted to `Wer.dll` from System32 and required exports are checked. Non-Windows/unsupported ABI/API returns Unsupported, inaccessible/missing/denied stores return Unavailable, ordinary native failures remain Failed or Partial, and successful sources remain useful when another store fails. No policy change, credential collection, elevation or filesystem fallback is attempted.
- Native WER store calls are synchronous and have no documented forced-cancellation API in this contract. Cancellation and a **20-second cooperative budget** are checked between calls. A native call can outlast that budget. The caller independently waits at most **22 seconds** or until user cancellation, then returns Unknown or a caller-cancellation-requested result with explicit pending-native wording and no inferred store report. This bounds the view's wait; it does not abort a native call or prove native cancellation/completion. `HasPendingNativeRead` exposes the gate for continuing UI feedback.
- A single-worker gate prevents overlapping native WER readers even if a caller stops waiting. A retry while that worker still runs returns Unavailable with a wait/retry explanation. The gate is released only when the worker has actually finished its cleanup. A detached late task fault is observed without logging exception details or altering the earlier Unknown/cancellation-requested result. Do not kill a service/thread/process, close a live store from another thread as an invented cancellation mechanism, or reuse the metadata child-process kill runner for this direct native API.
- Stores, keys and caller-owned buffers are released in finally paths. The native worker observes cancellation after the current synchronous call returns; the bounded caller may already have returned its explicitly qualified cancellation-requested state. No partial successful report is invented from cancellation. No external polling, reminder, scheduled task or background WER collection is created.

## Acceptance and remaining Windows validation

Portable tests exercise minimized projection, exact UTC windows, native timestamp/GUID rejection, duplicate/conflicting IDs, source-specific cross-store observations, missing/inaccessible/unsupported/failed/partial states, limits, inconsistent counts, cancellation, bounded caller timeout/cancel with a still-incomplete worker, late completion/failure and the public no-private-fields schema. They use synthetic metadata only; they do not open native WER stores, generate reports or prove Windows behavior.

Before claiming native support verified, run the reader unelevated on a disposable Windows runner/VM with the current SDK/OS recorded. Verify the V1 ABI against SDK headers, required exports, empty/inaccessible stores, existing readable metadata when available, per-store limits/change races, key/store lifetime, cancellation-between-calls and single-worker retry behavior. An empty runner cannot prove the populated-report marshalling path works. Do **not** force a crash, queue/submit/archive/delete a report, enable dumps, export Report.wer or read dump contents to make a smoke test pass. If suitable existing metadata is unavailable, mark that validation inconclusive/unverified rather than fabricate a result.

Record actual store access outcomes, coverage and ABI/runtime limitations separately from D1a and from servicing checks. The latter remain distinct explicitly requested operations with their own permissions and safety contracts; D1b does not authorize any repair.
