# Selected shortcut action research

S2 production actions remain unavailable. The separate owned native NT primitive test has passed; Win32 controls and the mapped-write witness remain inconclusive. Selected file/target evidence and optional aggregate DACL observations are implemented read-only, with owned Windows file/DACL fixtures and initial panel proof recorded in the execution ledger. No App action, production Windows executor or client-file move is enabled. This document does not certify immutable bytes, effective access, ownership, privacy or durable recovery.

## Supported rename primitive and limits

Microsoft's [FILE_RENAME_INFO reference](https://learn.microsoft.com/windows/win32/api/winbase/ns-winbase-file_rename_info) documents a destination relative to an open directory handle through `RootDirectory`. Classic `FileRenameInfo` (information class 3), passed to [SetFileInformationByHandle](https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle), binds the operation to the open source object. `ReplaceIfExists=false` causes an existing destination to fail. A possible S2 design must verify matching source/vault volume identities, use one validated relative destination component, and reject collisions without overwrite or a copy/delete fallback. A random name alone is not collision protection. No DeleteFile, IFileOperation, delayed restart operation, target action or POSIX override is proposed.

The selected object must be the `.lnk` itself, with a known full volume plus 128-bit [FILE_ID_INFO](https://learn.microsoft.com/windows/win32/api/winbase/ns-winbase-file_id_info), link count one, bounded bytes and supported attributes. A historical path or equal bytes alone is insufficient: identifiers may be reused after an object is gone.

Current S1 uses `IPersistFile.Load(path)` and separate read leases. These path readers cannot simply coexist with a no-share action handle. A proposed handoff retains a separate attribute-only identity anchor while COM/data readers finish, then opens the exact source path exclusively and compares its full identity and bounded bytes with the observed object. Directory ancestry leases remain held. [CreateFileW](https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-createfilew) documents sharing rules and the attribute-access exception; the exact anchor/readers/exclusive-handle combination still needs an owned Windows fixture. No close-and-path-move fallback is acceptable if that handoff fails.

No-share access is **not proof of inactivity or immutable contents**. Existing mapped views are a material exception: [LockFileEx](https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-lockfileex) explicitly says mapped reads/writes are not prevented by its locks. The development witness must demonstrate the actual boundary rather than claim that an exclusive open or a byte lock freezes every writer. Any future shortcut workflow must describe its precise object-bound, point-in-time contract. This does not relax cleanup's active-use gates or duplicate review's retained-copy protection requirements.

## Privacy and recovery are separate gates

The official [file security and access rights guidance](https://learn.microsoft.com/windows/win32/fileio/file-security-and-access-rights) states that a new default security descriptor is assigned on creation, **not rename/move**, and that a parent's security descriptor does not control access to a child file. A private folder therefore does not by itself make an incoming, broadly readable shortcut private. A restricted initial design could require an already verified private source DACL. More general support needs a separately reviewed, explicit file-ACL change and recovery policy; no such mutation is enabled here. [SetSecurityInfo](https://learn.microsoft.com/windows/win32/api/aclapi/nf-aclapi-setsecurityinfo) has additional inheritance and access semantics; a NULL DACL must never be mistaken for restricted access.

A bounded private journal and a successful rename are separate operations. [FlushFileBuffers](https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers) documents flushing a file's buffers; it does not promise an atomic journal-plus-rename protocol or guaranteed power-loss recovery. Intent, native outcome, observed destination identity and completed recovery records must remain distinct. Uncertain outcomes need an Unknown/review-needed result, with no automatic compensating path action. Quarantine preserves an object rather than freeing its content allocation; restore points do not recover deleted files.

Undo must begin with a fresh user selection of the actual quarantined object and a separately reviewed exact local restore destination. A journal's creator, original path, ownership marker or readable metadata is not blanket restoration authority. Fresh source identity/bytes, destination ancestry, volume, permissions and collision checks remain necessary. No overwrite, automatic restore, arbitrary journal-supplied source, or cross-volume fallback is proposed.

## Next acceptance stages

The [owned directory-guard compatibility matrix](SHORTCUT-DIRECTORY-GUARDS.md) now isolates source-parent, destination-parent and ancestor sharing changes before considering a client move. Baseline native success does not establish operation compatibility under stronger guards or protection from concurrent namespace changes. No production gate is enabled by this experiment.

1. **Owned development primitive/witness:** validate only disposable fixture files and folders; test handle-bound relative rename, same-volume checks, no-overwrite collision, identity/byte observations, explicit restore and the mapped-write limitation. Native success would establish only those observations on the tested Windows build. It would not prove the entire S2 workflow, private ACL policy or crash recovery.
2. **Read-only client eligibility/preview producer:** collect fresh real shortcut identity, bounded bytes, DACL and supported target-availability evidence, retaining source/time/coverage and uncertainty. Keep `CanMove=false` until the remaining action and recovery gates are reviewed and validated. S1's selected recheck remains read-only and is not an action token.
3. **Separately reviewed future action:** exact user selection/preview/acknowledgment, fresh guarded KnownMissing target evidence, supported handle handoff, an eligible same-volume recovery location, private storage policy, bounded journal and honest per-item outcomes. Only the selected shortcut object may move; its target/application/data must never be changed.

Protected system/application/data/save/settings/credential roots remain excluded. Actual user/common **Startup folders must also be excluded**, so S2 cannot bypass the separate startup-action gates. Unknown, offline, network, unsupported, inaccessible, changing or restored-target evidence blocks a missing-based action. A future explicit recoverable shortcut move may honestly use point-in-time absence evidence; it need not pretend the target will remain absent forever.

Official Microsoft API/guidance sources above were rechecked during the planning review. No native action, build or client-machine operation was performed to write this document.

## Implemented development-only primitive probe

`tools/MadClean.WindowsSmoke/ShortcutRenameProbe.cs` now implements the narrow owned-file proof only. Its one background STA worker validates the harness's exact GUID root/marker, creates one fresh child atomically, and uses the existing trusted shortcut-creation fixture for links to an owned sentinel. Nothing in the application or production Windows assembly calls this probe.

The probe retains a metadata-only identity anchor while opening the same file for exclusive read/DELETE, checks full128-bit identity/volume/link-count one, and uses basic FileRenameInfo with a held directory and one generated relative .lnk name. It observes move and restore through the same file handle, no-overwrite collision refusal, identity/byte preservation and unchanged target. It has no copy/delete fallback or rename Ex flags. These are momentary facts in a disposable owned tree, not stable contents or adversarial namespace/recovery proof.

A separate mapped-file case closes its original file/mapping handles while retaining a writable view, then tests whether a new exclusive handle can coexist with an observed mapped write. A positive result demonstrates why exclusivity cannot be interpreted as inactivity. Unsupported mapping remains unverified and cannot fake a witness; the core rename facts are qualified separately.

A45-second caller wait only requests cooperative cancellation. Native/COM/view/CTS ownership remains with the worker; no caller deletes its tree or force-closes handles. Teardown enumerates only the known bounded non-reparse child after resources close. Unknown commit/cleanup, pending work or failed teardown retains the entire outer fixture and marker and skips later transaction probes. The SDK compile probe independently checks x64 rename-header offsets. Fixed report fields contain only state/bools/native code/reason, never source paths, IDs or bytes.

## Separate native compatibility experiment

The development harness now has an explicitly selected third backend on a fresh owned child. It calls the OS's loaded System32 `ntdll.dll` export `NtSetInformationFile`, using `FileRenameInformation` (native class10), through control ABI2. This is a separate compatibility experiment, never a retry or automatic fallback for either failed Win32 check. No production assembly imports it, and its result cannot enable a client action or promote another backend's status.

The [official native function contract](https://learn.microsoft.com/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntsetinformationfile) explicitly distinguishes user-mode Nt calls from Zw calls. The [native rename structure](https://learn.microsoft.com/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) documents relative directory handles and same-volume rename requirements. The installed SDK independently checks NTSTATUS width and IO_STATUS_BLOCK layout; it does **not** independently declare this function or native class10 in its partial `winternl.h`. The function-pointer definition/class value therefore depend on those reviewed official native sources. This carries an additional [internal-API compatibility burden](https://learn.microsoft.com/windows/win32/devnotes/calling-internal-apis), not evidence of a generally supported production fallback.

The experiment keeps the existing source rights, bounded relative leaf, no-overwrite rule, identity checks, same-volume restriction and actual move/restore readback. It reports NTSTATUS values separately from genuine Win32 setup failures. An immediate STATUS_PENDING is not success: the worker retains the native buffer, IO_STATUS_BLOCK, source handle and module reference until source completion and an observed terminal status. An unexpected wait failure or still-pending status retains that native worker indefinitely rather than freeing potentially live I/O memory. The caller's45-second deadline reports unverified ownership, retains the entire fixture tree and skips later mutation fixtures. Nothing force-closes or cancels that native I/O.

A positive experiment requires three actual NT calls, two terminal-success operations with verified move/restore readback, an observed negative collision refusal, all prior identity/bytes/target invariants and safe teardown. Source review and compilation alone cannot establish these observations. Actual Windows results for this increment remain pending.
