# Owned journal-store boundary

This is a development-only prerequisite for future diagnostic operation records. It does not create a production journal, access LocalAppData, parse operation history, reconcile a process, launch DISM/SFC, request elevation or enable the immutable production execution gate. The existing dormant production logger is not replaced or certified by it.

The internal factory accepts only a matching owned GUID artifact root and four fixed case names. There is no arbitrary destination or production-scope entry point. It validates the ordinary root ancestry and exact owner marker, checks persistent ACL support on the held volume, and creates a new fixed leaf/file with explicit protected current-user and SYSTEM full-control ACLs. Actual owner and exact DACL policy are then read back through the held handles. Existing objects must pass the same checks; creation descriptors do not repair an existing object's permissions. No ACL is modified after creation.

Ordinary-object, full native file identity, link count, final path and size guards apply before content access. The fixed `intent.bin` file is limited to 4,096 bytes and held with exclusive sharing. Newly created empty files accept only one constant inert payload, using WriteThrough and an explicit disk flush followed by same-handle readback. Reopening an existing file verifies exact fixed bytes without replacement or repair. This is not a real launch intent or status interpretation.

Native security descriptors are API-owned allocations. Length is bounded after return before copying, temporary copies are cleared, and LocalFree is checked. Uncertain cleanup latches further store attempts and retains the owned fixture tree. The factory does not claim that its managed cap limits native API allocation.

The required native fixture independently audits actual owner/DACL facts, checks same-process exclusive-open refusal, existing-file reopen, and rejects separate newly owned leaves with an extra-principal ACL, reparse point or oversized file. It verifies the oversized file's length remains unchanged; it does not claim a full-content comparison. Its created test link is removed only after exact link/target/ownership checks, nonrecursively, with the ordinary empty target audited afterward. Unknown prerequisites or symbolic-link permission remain inconclusive. Prior cleanup uncertainty cannot be cleared by another invocation.

Reports contain fixed states, booleans and actual optional native status only. No SID, ACE bytes, descriptor pointer, owner nonce, path, arguments or payload is exported. Explicit access-control facts do not prove authorship or protection from the same user, administrators or SYSTEM. One exclusive file is only a cooperating-open boundary for that exact store, not machine-wide servicing coordination.

## Sources and validation

Creation/flush semantics were checked against current official Microsoft sources: [CreateDirectoryW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createdirectoryw), [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [GetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo), [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers) and [FileStream.Flush(Boolean)](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.flush). In particular, an existing object's security is not reset by CreateFile's creation descriptor.

Independent source review corrected sticky cleanup, exact link-only teardown and an overbroad unchanged-file claim; no material blocker remains in the reviewed boundary. Actual Windows evidence is pending. A production fixed per-user store, cross-instance/crash observations, bounded versioned record parsing, durable unresolved-intent reconciliation, bounded UAC dispatch, actual servicing/result logs and user-reviewed operation validation remain separate stages. Flush/readback does not guarantee every power-loss or launch-atomicity scenario.
