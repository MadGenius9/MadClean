# Separate disposable MSI request qualification

The fixed `--msi-request-validation` development mode is separate from ordinary inspection, the passive Windows harness and the distributed app. It requires the explicit mode flag, GitHub Actions, a GitHub-hosted Windows x64 runner, the exact repository/feature branch, source/run/attempt context and repository workspace. It does not run on a personal PC or self-hosted runner. The public production uninstall guard remains false until the separately reviewed source-bound qualification is complete; this mode is not a client environment override.

The mode creates exactly one fresh GUID-owned scope under `artifacts/msi-request-validation-<GUID>` with a matching 32-byte ownership marker. The product code is that GUID; component, upgrade and package codes are fresh independent GUIDs. Before setup, complete current-user plus machine `MsiEnumProductsExW` enumeration for this exact code must observe no instances. A collision refuses all product actions; it is never cleaned up as a fixture product.

The package is authored locally through supported Windows Installer database APIs. It contains one fixed inert text file, targets only the fresh scope's target directory and uses current-user unmanaged registration. There are no downloaded tools/packages, custom actions, binaries, transforms, service/registry/upgrade/remove-file tables, arbitrary properties or reboot actions. All persisted tables and exact property, sequence, file/component/directory, media and UI rows are read back before setup, along with the x64 summary/template and package identity. The database, source payload, marker and ancestor ownership stay held through installer operations. Failure to establish this contract is not successful qualification.

Fixture setup uses `MsiInstallProductW` only for this freshly authored inert package, with per-user properties and restart suppression. Its process-local setup UI level is explicitly changed and restored with observed API results. This setup-only suppression is never a production uninstall option. After actual setup returns, the exact product must appear only in UserUnmanaged context and the owned target payload must match its fixed contents before a request is prepared.

The uninstall request goes through the common new Windows backend and the same fixed `/x {ProductCode} /norestart` visible-client route. Its internal fixture authorization accepts only the exact marked scope, canonical same-GUID product and fixed fixture metadata. Public client dispatch cannot be enabled by these environment variables. The fixture borrows a read-only view of the actual retained client process; it does not reopen a PID or expose kill/close/start operations. UI Automation is restricted to windows of that live client. It may acknowledge only the exact English generic uninstall question and its Yes control, then must observe and explicitly invoke the fixed authored inert-product Remove dialog. Unknown or localized UI is inconclusive; there is no quiet/passive fallback. No screenshot or raw window text is exported.

After the actual client exit, engine status, complete current-user/machine product-code absence and owned payload absence are observed independently. An exit code is not a global uninstall/health verdict. The target directory may legitimately be absent; access failures, replacements and reparse points are not absence. Exact known fixture files are removed without recursion only after all worker/native/process ownership has settled, marker validation succeeds and the product/payload are observed absent. Unexpected entries or ownership/operation uncertainty retain the whole scope. No raw registry/cache cleanup or force deletion of application files occurs.

No local watchdog kills Windows Installer, a process tree, service or MSI native call. A pending call remains owned. The disposable CI job's outer VM lifetime is independent of MadClean cancellation/rollback. If the job expires, its last fixed facts remain incomplete and cannot qualify production dispatch. A process crash loses in-session observations; no PID-based recovery or fabricated completion is supplied.

Only `artifacts/msi-request-validation/report.json` is uploaded, with fixed states/nullable booleans, exit statuses and source/run/attempt/time. Product codes, process IDs, paths, package names, raw provider/installer text, MSI files, payloads and executables are not uploaded. The existing atomic verification publisher admits this as a separate fixed `msi-request.json` file after strict schema/context/coherence checks. Missing/rejected MSI facts do not hide independent passive/core evidence; the latest summary reports the MSI job, artifact and qualification separately. Legacy/passive success never grants MSI dispatch permission.

## Exact selected-product preparation (report version 3)

The v3 fixture retains every v2 legacy binding observation without promoting a blocked binding or historical Partial global inventory. It independently creates the new source-bound selected-product selector from the actual snapshot and selected row, then reads exactly three supported ARP provenances for the owned ProductCode and current-user plus machine native MSI contexts. Source hive is provenance, not a derived native context. The new common backend repeats this preparation immediately before its one-shot visible client request. The old read-only binding policy and its reports remain unchanged.

A separate nullable `targetPreparation` object projects only the actual immutable target report: result/state/reason/coverage, exact lookup counts, single-present source-match and restriction flags, native completeness/issue/instance counts and single context, historical global state, and current-global-not-read facts. Missing immutable preparation leaves the object null. No identifiers, compared values, registry paths, messages or product metadata are exported. Current-global-not-read describes this exact-target read; the separate legacy binding diagnostic can have made its own global refresh.

Positive v3 evidence requires three lookups, one present and two absent with no unknowns, matching original provenance, observed SystemComponent=false, WindowsInstaller=true and NoRemove=false, complete native enumeration with zero issues and exactly the owned UserUnmanaged context. Target state/reason must be ObservedMatch with Available target coverage, while result state preserves Available or Partial historical coverage. It also requires the same actual qualified tool, authored visible consent, client exit 0, independent exact-code/payload absence, settled ownership and owned teardown. Target facts alone do not grant execution, baseline, leftover, global-absence or uninstall-success permission. Legacy v2 acceptance remains unchanged and cannot use v3 facts to pass.

This is a source-bound candidate-backend qualification, not proof of the WPF Prepare/acknowledge/confirm cycle or general installers/contexts. Production dispatch remains disabled pending matching actual evidence and separate review. Linux evidence-schema tests establish neither Windows target coverage nor visible installer behavior.

## Visible consent observation (report version 4)

The v4 report adds only fixed diagnostic observations from the same borrowed live client and existing UI Automation route. It records whether the owned client PID and owned windows were observed; whether the exact authored/generic titles, visible/enabled windows, fixed controls and Invoke patterns were reached; whether the known generic question matched; and whether the existing guarded Invoke calls actually returned success. Booleans are sticky once true. False means an actual relevant observation was negative, while an unreached branch remains null. No PID, window title/text, arbitrary controls, paths or screenshots are exported.

The actual polling-iteration count is bounded to 4096; overflow remains null rather than a capped claimed count. A separate nullable enumeration-failed fact refers only to an actual UI Automation FindAll failure, not every UI error. A managed exception HResult records the actual callback exception and is rethrown as before. Periodic report writes are bounded to approximately one second, with final/stage writes. The already observed immutable tool identity is projected at callback entry as well as after the backend returns, so a pending client does not erase actual completed trust observations.

The fixed 90-second observation window, exact live-client/window/English-question restrictions, original control predicates and existing Invoke route remain unchanged. Expiry is unverified consent, not cancellation, client exit, completed uninstall or permission for another route. There is no additional dialog acceptance, foreign-window inspection, quiet retry, process kill, force closing or teardown beneath a pending owner. Version 2 and 3 acceptance remains unchanged; v4 additionally requires a coherent actual authored Remove Invoke observation for positive visible-consent proof. Diagnostic fields never enter Core authorization.
