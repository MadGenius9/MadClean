# Cleanup action gate — strict identity and active-use blocker

**Permanent cleanup execution is Unsupported under the current strict safety contract. No cleanup executor is implemented or enabled by this document.** Existing previews and exclusions remain read-only with respect to inventory files. Authorizing development of the roadmap is not a request to act on a user's PC. This research executed no file disposition, recycle, rename, oplock/IO-control or deletion operation.

The blocker is specific: supported open-handle identity can bind an operation to a selected object, but the reviewed APIs do not establish an atomic freeze of **all** required active-use, stream, metadata and protected-scope predicates through a cleanup commit. An API returning success or a fixture passing is not evidence for an undocumented stronger guarantee. Do not relax the policy or enable a path-based fallback to mark this stage finished.

## Exact-target preparation is necessary, not sufficient

Any future executor must have separate mutation contracts and source ownership. Current `CleanupCandidate` metadata, duplicate observations and F1 read handles are not deletion capabilities. Do not expose `Execute(path)` or accept arbitrary UI/configuration paths as trusted selections.

A later reviewed preparation design would require all of the following before presenting an eligible action:

- Explicit user selection from a current supported-temp preview, no preselected removal, a current readable exclusion revision, and a separate fresh exact-change confirmation. The confirmation must disclose irreversible/recovery limits, permissions and actual selected paths. Expired or changed previews require a new review; development authorization is not runtime confirmation.
- Revalidate the actual fixed-local known temp root, lexical protected scopes and registered/shared/application/credential/data exclusions. Restrict the first slice to individually selected regular files; never widen to folders, a whole drive, arbitrary paths or a recursive delete.
- Acquire fresh supported handles and validate the canonical path, volume plus full 128-bit file ID, observed logical size, write/change stamps, age and supported stream scope. Reject unknown identity, multiple links, readonly/system/hidden/encrypted/offline/recall/reparse objects and missing/inconsistent data. Never clear readonly attributes, weaken ACLs, hydrate files, force-close another application or silently elevate to make an item eligible.
- Retain the exact target handle and required parent/root leases through the action. A different object at the old pathname cannot replace it. Maintain appropriate cancellation, expiry and conflict handling without blocking another application indefinitely. Root-to-leaf validation and directory handles reduce namespace races; they are not a universal proof that every metadata/reparse/policy predicate cannot change.
- Demonstrate the required active-use and consistency guarantees using supported, documented mechanisms on the supported platform. If they cannot be established, return Unsupported/Blocked with the reason. Do not rename an imperfect test into proof of safety.

## Why an exclusive RWH oplock does not clear the strict blocker

The relevant current official sources are [FSCTL_REQUEST_OPLOCK](https://learn.microsoft.com/windows/win32/api/winioctl/ni-winioctl-fsctl_request_oplock), its [input](https://learn.microsoft.com/windows/win32/api/winioctl/ns-winioctl-request_oplock_input_buffer) and [output](https://learn.microsoft.com/windows/win32/api/winioctl/ns-winioctl-request_oplock_output_buffer) buffers, [request/grant conditions](https://learn.microsoft.com/windows-hardware/drivers/ifs/granting-oplocks), [create semantics](https://learn.microsoft.com/windows-hardware/drivers/ifs/irp-mj-create2), [set-information semantics](https://learn.microsoft.com/windows-hardware/drivers/ifs/irp-mj-set-information2), [section synchronization](https://learn.microsoft.com/windows-hardware/drivers/ifs/fs-filter-acquire-for-section-synchronization2) and [breaking oplocks](https://learn.microsoft.com/windows-hardware/drivers/ifs/breaking-oplocks).

- For a local asynchronous stream, a REQUEST for Read-Write-Handle (`CACHE_READ | CACHE_WRITE | CACHE_HANDLE`) returning `FALSE / ERROR_IO_PENDING` means the oplock **was granted**, not merely queued for a future grant. The request remains pending until a break. Other opens must meet the documented oplock-key conditions, and writable user-mapped sections prevent this grant.
- The grant condition excludes **writable** mapped sections. It does not state that no readonly mapping, attribute-only user, application dependency or other active use exists. The lock is stream-scoped; it is not a blanket lease over every ADS, parent directory and policy predicate.
- Attribute-only `READ_ATTRIBUTES`, `WRITE_ATTRIBUTES` or `SYNCHRONIZE` opens are explicitly exempt from the ordinary create-time oplock break rules. The set-information operation table does not establish a universal immutable basic-attribute/ADS/protected-scope predicate. Do not interpret a quiet event as proof nothing relevant changed.
- Creating a writable mapped section (`PAGE_READWRITE` / `PAGE_EXECUTE_READWRITE`) breaks modern oplocks, including RWH, to None **without acknowledgment**; that operation proceeds immediately. Therefore “withhold ACK while committing” is not a general freeze.
- A pending operation's event/completion/output can be inspected without sending ACK. Only an output with `ACK_REQUIRED` carries the documented original-level-until-ack condition. Any break/downgrade, cancellation, handle close/switch or unexpected state invalidates a proposed lease. Detecting an unbroken event, then issuing disposition, is not an atomic conditional check-and-delete API.
- Classic disposition on the **same retained handle/oplock key** is not documented to break its own RWH; the disposition break rule concerns a different key with DeleteFile=TRUE. That permits an attempt subject to OS restrictions, not proof that all eligibility predicates remained true through commit. Atomic create-with-oplock can narrow a separate open/request window; it does not solve this later predicate/commit gap.
- A future experimental lease implementation would need correct pinned-buffer/OVERLAPPED/event lifetimes, completion draining and prompt conflict release. Some ACK-requiring conflicting operations can wait indefinitely; a utility must not hold another application hostage while waiting for user confirmation. Cancellation is not permission to free buffers still owned by pending native I/O.

These limits mean RWH cannot honestly be labeled **all-active-use exclusion** for this executor. Windows fixture results are necessary to understand supported behavior, but cannot upgrade a narrower documented contract into a stronger claim. A future supported design must prove the required guarantee or explicitly remain Unsupported; this document does not authorize a narrower or relaxed policy.

## Recoverable vault: separate unimplemented design, no space reclaimed

[FILE_RENAME_INFO](https://learn.microsoft.com/windows/win32/api/winbase/ns-winbase-file_rename_info) documents handle-based rename, an optional directory handle for a relative new name, and collision failure with ReplaceIfExists=FALSE. A separately reviewed same-volume private vault could potentially use the retained source handle plus a validated vault directory handle and a generated single-component relative name to maintain identity binding. This is **not implemented** and does not resolve the strict active-use/predicate blocker above.

A move on the same volume frees **no file-content allocation**. It must be labeled a staged move, never reclaimed disk space. Different-volume handling is Unsupported; no copy/delete or permanent-delete fallback is assumed. No existing destination may be overwritten.

Before a recoverable vault could ship it would need restrictive directory **and file** security (a rename may retain a permissive source DACL), no reparse/redirected destination, verified identity/stream/metadata handling, a minimal protected manifest, crash recovery, restore collision blocking, explicit retention/purge rules and privacy review. Temporary files can contain secrets; hiding a folder is not protection. Moving a file or preserving bytes is not a guarantee of complete ACL/metadata restoration. Do not create persistent backup contents or claim undo without this design and validation. Restore points do not recover deleted files and are not a firmware/file recovery guarantee.

## Honest outcomes and next validation gate

Any later native action would distinguish Blocked, CancelledBeforeCommit, DeleteRequested, DeletePendingObserved, HandleClosed, NameAbsentObserved, Indeterminate and Failed. A successful disposition request can be a commit point: cancellation afterward cannot promise rollback, and remaining uncommitted items should stop with actual per-item outcomes. Even observed pathname absence is not proof of physical reclamation or destruction of every remaining reference/mapping. A selected file's logical size is not guaranteed reclaimed bytes.

Before enabling any executor UI, add separate Windows tests using **only repository-owned disposable fixture files**, never actual user/System Temp contents. Use a test-only trusted-scope policy that cannot be enabled as a production arbitrary-path override. Validate exact selection/identity, changed/replaced paths and ancestors, readonly/ADS/hardlinks, existing ordinary handles, writable and readonly mappings after source handles close, attribute-only accesses, permission denial, oplock grants/breaks, cancellation before/after a native commit and pending deletion with outstanding metadata handles. Do not skip the mapped/metadata cases or suppress native errors to pass a test.

The runtime user gate must still be explicit selection followed by separate confirmation of a fresh exact preview, with irreversibility, recovery and permission limitations visible. Native Windows tests and an independent review are prerequisites, not replacements for the documented safety guarantee. Until that guarantee exists, the current result is **Unsupported / no executor**, not an unfinished unsafe fallback disguised as a completed cleanup action.

The new [owned shortcut primitive/mapped-view probe](SHORTCUT-ACTION-RESEARCH.md) does not alter this cleanup gate. Cleanup rows now explicitly label active use Unknown: excluding sharing conflicts does not prove the absence of surviving mappings. A positive handle-rename fixture must never be reused as cleanup or duplicate-keeper authorization.
