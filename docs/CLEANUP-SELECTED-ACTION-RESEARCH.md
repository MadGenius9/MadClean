# Research: one selected cleanup-file action

Research only, 2026-11-03. No native query, disposition, deletion, cleanup, test, dependency installation or personal-PC operation ran. This document adds no executor, permission switch or relaxation of [the current cleanup gate](CLEANUP-ACTION-GATE.md).

## Supported primitive and its ceiling

Current official Microsoft documentation was retrieved and read from MicrosoftDocs/sdk-api for [CreateFileW](https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-createfilew), [SetFileInformationByHandle](https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle), [FILE_DISPOSITION_INFO](https://learn.microsoft.com/windows/win32/api/winbase/ns-winbase-file_disposition_info), [DeleteFileW](https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-deletefilew) and [UnmapViewOfFile](https://learn.microsoft.com/windows/win32/api/memoryapi/nf-memoryapi-unmapviewoffile). These are current published references, although individual articles retain older metadata dates.

The smallest supported exact-object permanent operation is classic **SetFileInformationByHandle(FileDispositionInfo, DeleteFile=TRUE)** on the same retained DELETE-capable handle. It is not a path-based DeleteFile fallback, recycling, a recoverable move or proof of freed storage. Do not open DELETE_ON_CLOSE while preparing a preview: that makes close itself destructive and FILE_DISPOSITION_INFO says its Boolean has no effect for such a handle. Do not use EX/POSIX, ignore-readonly flags, mapped-file bypass, ACL/attribute changes, forced application closure or elevation.

CreateFileW documents that share-zero prevents subsequent read/write/delete opens, and incompatible existing access fails with ERROR_SHARING_VIOLATION. It also expressly says **attribute and extended-attribute access is unaffected by the sharing flag**. FILE_FLAG_OPEN_REPARSE_POINT addresses the final opened link; it is not an ancestor no-follow guarantee. Retained root/ancestor guards plus full canonical identity checks remain necessary. DeleteFileW's mapped/open-handle restrictions cannot simply be promoted into an undocumented universal guarantee for every same-handle SetFileInformationByHandle operation.

UnmapViewOfFile states that a view can outlive the creating file handle and that Windows holds such a file open until the last view is unmapped, with no sharing restrictions. Therefore neither successful exclusive open nor a passed ordinary-writer conflict case by itself proves all mappings or other application reliance are absent. File age is a selection rule, not proof an application no longer needs its contents.

## Smallest candidate contract, if its missing guarantee becomes established

A future production action would accept one sealed selection from a completed supported-temp report, never an arbitrary path argument. It would reacquire actual fixed-local roots/protected known-folder exclusions and the current saved-exclusion revision; require an old regular non-reparse single-link file, supported unnamed-only stream scope and full volume/128-bit identity/stamp consistency; reject unknown roots, metadata, exclusions or permissions. It would retain the exact target and relevant namespace guards from fresh review through the one-shot decision and request. Source/selection/exclusion changes, cancellation, expiry or changed native facts before reservation refuse without disposition.

Only a separate exact-path preview and affirmative runtime selection could authorize the request, with permanent-deletion/recovery limits disclosed. Root guards must not be held indefinitely while waiting for a user: bounded expiry/conflict handling must release them without mutation. Preparation must not clear attributes, hydrate files or modify ACLs. A final same-held check is useful but cannot be described as atomically freezing every policy predicate.

After reservation, observe each stage independently: actual disposition attempted/result/error; optional DeletePending; checked target close; actual subsequent namespace observation; ownership released or uncertain. A name lookup can find a replacement, so identity-safe disposition and later path observations must remain distinct. Stop after the commit boundary cannot promise rollback. Remaining handles/mappings, filesystem accounting, compression, hard links and storage behavior preclude reporting selected logical bytes as actually reclaimed. No result implies restored files or recovery through a restore point.

This is a description of the minimum request boundary, **not authorization to enable it under the current unresolved gate**.

## Concrete remaining gate and stop reason

The current production contract asks for proof of active-use exclusion and a freeze of all stream/metadata/protected-scope predicates through commit. The retrieved Win32 contracts establish ordinary sharing exclusion and exact-handle disposition, not that stronger universal statement. Attribute-only access is an explicit exception. Existing RWH research already explains why oplocks do not supply a general freeze or readonly-mapping/application-dependency proof. Enumerating foreign processes, Restart Manager, more age thresholds or another fixture would not establish the missing guarantee.

The actionable stop reason is therefore **Active-use / policy-commit consistency not established by supported API contract**, with the relevant actual sharing refusal retained when observed. Keep production CanDelete/ExecutionSupported false and the ordinary scan/preview/exclusions useful. A native error remains its actual error; do not relabel every refusal as a known mapping or active application.

This is a contract boundary, not an assertion that same-handle deletion is unsupported on Windows or that all engineering risk can be eliminated. Exact retained identity prevents substituting a different object at the commit call; it does not defend against every same-user adversary, privileged agent or application dependency. A future independently reviewed product contract could explicitly distinguish documented OS conflict refusal from the unprovable claim that a file is universally inactive, but this research does not adopt that narrower policy or weaken the existing active-file protections. Until the missing guarantee is supplied or the product contract is deliberately reviewed, further duplicate disabled executors add no completion evidence.
