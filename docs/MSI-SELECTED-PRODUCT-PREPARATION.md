# Read-only exact-product MSI preparation

This is a separate metadata boundary for one explicitly selected registered ProductCode. It never starts Windows Installer, changes registry data, requests elevation, reads a package/source path, or grants execution permission. Existing read-only registration/binding reports and their source-to-context policy remain unchanged. A later action consumer requires its own reviewed selection, qualification and dispatch contract; diagnostic reasons or changed-field masks cannot authorize it.

## Scope and actual observations

`MsiSelectedProductPreparationPolicy.CreateScope` requires the actual selected record reference exactly once in its bounded Available/Partial inventory. The selector freezes the original required registration/provenance evidence, historical global coverage, generation and original two-minute read lifetime. It rejects malformed/null source rows, unsupported source syntax and stale facts. Invalidation is one-way and cannot make an old report current again. A separate Core request intent may atomically consume this selector's lifecycle under the same lock; its internal callback performs only managed reservation checks/assignment. Invalidation before that boundary prevents consumption; after a committed boundary it cannot pretend to revoke an already reserved request. Consumed selectors cannot start another fresh read. This coordination supplies no dispatch authority itself.

`WindowsMsiSelectedProductPreparation.ReadAsync` performs three exact-GUID lookups: HKCU shared, HKLM 64-bit and HKLM 32-bit. It does not enumerate unrelated applications or construct a filtered global inventory marked Available. Each lookup records actual Absent, Present or Unknown state. Absence requires a returned missing-key/path code, never a managed null or an inferred native error. Access denial, registry links, unavailable roots and other unresolved observations stay Unknown. Unsupported 32-bit processes/platforms are refused before querying, rather than inventing HKLM64 absence.

Registry components are opened read-only with `REG_OPTION_OPEN_LINK` and checked through a NULL-data `SymbolicLinkValue` type query. A link or unqualified topology is refused; no link target is read or followed. HKCU uses `RegOpenCurrentUser`; impersonated callers are refused. The reader requests no user SID or other-user scope. It uses the existing fixed-capacity whitelist decoder for DisplayName, DisplayVersion, Publisher, SystemComponent, WindowsInstaller and NoRemove. Missing flags retain the existing declared-false semantics; invalid flags remain unknown. UninstallString and QuietUninstallString receive existence queries with NULL data only. InstallLocation and command contents are not read.

The original source must still supply exactly one registration for that GUID, with no competing registration in the other covered sources. Required text and mechanism/restriction facts must be known, SystemComponent must be false, WindowsInstaller true and NoRemove false. Name, version, publisher, original source/identity and mechanism/restriction observations must retain the selected values. Optional historical installation-path metadata is not promoted or used as a target.

The existing raw native reader then enumerates only that ProductCode across current-user managed/unmanaged and machine contexts (`1|2|4`), with NULL SID input/output and the same bounded property whitelist. It requires complete enumeration and exactly one Installed instance with matching product/name/version/publisher. Advertised, missing, unknown, duplicate, changed or incomplete native facts cannot yield an ObservedMatch. Native context is an actual independent observation; an ARP hive is provenance and is not relabeled as proof of that context. This does not mutate the original read scope's legacy 3/4 hint or reinterpret an old SourceContextMismatch diagnostic as permission.

## Coverage, publication and ownership

`MsiSelectedProductPreparation` freezes copied lookup, registration-evidence and native-instance collections. `TargetCoverageState` describes this limited target read, not all installed applications. Historical global Partial remains Partial in a matching outer result, even when target coverage is Available. `CurrentGlobalSnapshotWasRead` is false and current global inventory is explicitly Not checked. The report's `CanExecute` is always false. These facts cannot qualify a complete leftover baseline, global product absence, removal safety, package authenticity or uninstall completion.

Selection generation, UTC freshness, one-way invalidation and cancellation are checked before work and publication. Actual publication time is checked independently of caller-supplied observation time, so an old CheckedUtc cannot revive an expired selector. Current observations remain sequential, not atomic source/context or historical object-identity proof. Invalidation/cancellation cannot interrupt or force-close a Windows API already in progress.

There is no independent concurrent registry gate: the worker acquires the existing MSI gate and then the existing ARP gate, and releases only gates it acquired. A separate scheduled-ownership count covers queued-but-unstarted work as well as execution; it is visible through `HasPendingNativeRead` before scheduling. Tasks and terminal observers are allocated before ownership registration. Scheduling failures release only a never-queued or terminal task; other ownership remains visible until completion. Caller timeout/cancellation never releases worker ownership. The cooperative whole-read budget is 20 seconds and the caller wait is 45 seconds; pending native work retains its handles and shared gates until it actually returns.

Names, ProductCodes and registration values remain in memory for explicit local review. Do not serialize whole reports into activity logs, screenshots, telemetry or CI artifacts; any development proof must project fixed states/counts and source/run context only.

## Official references and validation limits

Current official Microsoft SDK source pages were retrieved successfully and read on 2026-11-03:

- [RegOpenKeyExW](https://learn.microsoft.com/windows/win32/api/winreg/nf-winreg-regopenkeyexw) ([source](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/winreg/nf-winreg-regopenkeyexw.md)): read access, no creation, link-object opening and returned status semantics.
- [RegOpenCurrentUser](https://learn.microsoft.com/windows/win32/api/winreg/nf-winreg-regopencurrentuser) ([source](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/winreg/nf-winreg-regopencurrentuser.md)): current thread-token mapping, cached predefined HKCU limitations and the default-hive behavior when a profile is not loaded. This read does not certify profile ownership or identity continuity.
- [RegQueryValueExW](https://learn.microsoft.com/windows/win32/api/winreg/nf-winreg-regqueryvalueexw) ([source](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/winreg/nf-winreg-regqueryvalueexw.md)): NULL-data size/type queries, missing values and non-guaranteed string termination. The bounded decoder still requires actual correct terminators; it never repairs provider data.

The existing [MsiEnumProductsExW](https://learn.microsoft.com/windows/win32/api/msi/nf-msi-msienumproductsexw) contract requires same-thread enumeration until ERROR_NO_MORE_ITEMS and defines NULL-SID current-user coverage. This is not all-user enumeration or a context selector for a future msiexec command.

Portable tests exercise exact source/reference requirements, duplicate and unknown lookups, real absence-code requirements, restriction preservation, changed fields, native ambiguity/incompleteness, stale-time replay, cancellation and frozen output. They are synthetic metadata cases, not a Windows registry/MSI or queued-worker runtime proof. Windows native integration, access/link/profile policies and pending-call behavior remain unverified until matching-source evidence. No production dispatch gate is enabled by this reader.
