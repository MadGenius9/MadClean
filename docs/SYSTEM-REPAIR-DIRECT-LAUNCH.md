# Direct-launch ownership controller

This work advances the disabled repair backend's managed-start ownership boundary. The portable controller supplies explicit process, pipe, attribute-list and call-buffer ownership; a concrete disabled Windows adapter now replaces the old managed route. It supplies no permission to repair, Windows qualification or App workflow. There is no Process.Start fallback.

## Authorization and ownership

The controller accepts only the existing exact committed repair context and its one-shot dispatch permit. Targets expose no executable path, command line or numeric handle. A trusted native adapter must bind its private target to the actual held fixed-executable identity and revalidate its own concrete tokens, raw aliases and non-pseudo handles. Public abstractions are testable collaborator contracts, not capability proofs by themselves.

A cooperating process-rooted domain retains the actual owner before scheduling. It permits one owner and keeps a bounded spent-permit history; reaching that limit refuses work rather than evicting authorization history. This is not cross-process exclusion or a restart-recovery mechanism. After claim, caller departure never cancels or abandons native work.

Preparation owns three pipe pairs, the attribute-list backing allocation, the exact child-handle value allocation and explicit call-state storage. The last allocation covers native call buffers and process-information slots so failures cannot hide unmanaged allocations outside the retained owner. Native implementations must adopt successful returned handles into preallocated owned slots before allocating a managed result object. Partial/uncertain native allocation must retain the adapter's actual owner; returning null means definitely no allocation.

Parent ends are non-inheritable, child ends explicitly inheritable. The exact three child handles form the inheritance list. Both output readers start before creation; closing the parent stdin writer supplies no host-console input. The permit is claimed once immediately before the create callback. False native creation means known no child, and failed output fields are not ownership evidence. A throwing boundary remains uncertain and is never retried.

After successful creation, observation uses the original owned process handle. Parent copies of child ends close before waiting for output EOF. A primary-thread handle is separately owned and closed. Process signaling, literal exit code, both readers' EOF and worker release, and each resource's cleanup remain separate facts. Code259 after an observed signal is an exit code; code0 never proves repair or integrity.

No handle closes while its read/wait is pending. Incomplete reader evidence retains the owner even if a task ended. DeleteProcThreadAttributeList applies only to an initialized list and does not free backing memory; handle-value storage remains alive through deletion. Free/close attempts are one-shot. Unknown cleanup, a failed parent-writer close or invalid collaborator identity blocks further work; no kill, forced close, cleanup retry or PID reopening repairs that uncertainty.

## Current official-source basis

The coordinating task retrieved these current Microsoft references after this executor's proxy rejected direct retrieval. These are documented contracts, not locally captured bytes or runtime evidence:

- [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw): nonzero creation success, zero failure/GetLastError, explicit application name, writable Unicode command line; creation precedes completion of child initialization.
- [CreatePipe](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-createpipe): failed output handles are indeterminate; null security attributes create non-inheritable handles.
- [UpdateProcThreadAttribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute): real inheritable handle list, bInheritHandles true, value storage valid through deletion. [Initialization](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-initializeprocthreadattributelist) uses an expected-failure sizing call; [deletion](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-deleteprocthreadattributelist) returns void.
- [STARTUPINFOW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-startupinfow) and [STARTUPINFOEXW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-startupinfoexw): exact field layouts, reserved fields, explicit standard handles and extended structure size.
- [SetHandleInformation](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-sethandleinformation) and [CloseHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-closehandle): explicit flag mask and owned-handle close results; close does not terminate a process.
- [WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject): signal/timeout/failure are distinct; closing during a wait is undefined. [GetExitCodeProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getexitcodeprocess):259 alone is not lifetime evidence.
- [ReadFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-readfile): synchronous buffer ownership lasts until completion. Anonymous-pipe EOF is false with ERROR_BROKEN_PIPE. True with zero bytes can reflect a zero-byte write and must not become EOF. Other errors and cancellation requests do not prove completed I/O.
- [GetHandleInformation](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-gethandleinformation): BOOL with HANDLE/outDWORD flags; inheritance is0x1 and protect-from-close is0x2. [PROCESS_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-process_information) orders process/thread HANDLEs before process/thread DWORD IDs.
- CreateProcessW's explicit Unicode environment contains sorted null-terminated name=value entries plus an extra terminating null; null environment would inherit the caller. [Creation flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags) establishes CREATE_UNICODE_ENVIRONMENT0x400, EXTENDED_STARTUPINFO_PRESENT0x80000 and CREATE_NO_WINDOW0x08000000. Only reviewed required flags belong in the future adapter.

The portable API deliberately uses symbolic operations. The coordinating task subsequently verified the remaining definitions: CreateProcessW's complete ten-parameter pointer/BOOL/DWORD order; ERROR_BROKEN_PIPE109 and ERROR_INSUFFICIENT_BUFFER122 from [the official error table](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--0-499-); and expected sizing failure122 in [Microsoft's AppContainer example](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer). Only its attribute-sizing example applies; no AppContainer setup is authorized.

## Typed dispatch integration

The repair boundary now accepts a dispatch-session base with two owned alternatives: the existing client session and a sealed direct session binding the exact admitted kernel owner and permit. A refused replay session cannot stand in for an admitted owner even when its context matches. A shared internal evidence policy checks actual creation/completion packets without caller-supplied success flags.

An actual known-no-child result preserves its raw facts and does not invent a client, PID, exit code or cancellation. Intent remains unresolved via the existing ObservationLost grammar; real setup/journal/preparation cleanup can yield a history-only block rather than falsely reporting retained live resources. A created process with an observed signal but missing PID/code keeps those raw facts separately from the stricter client observation. Cleanup and unresolved history remain independent. Unknown creation, contradictory packets, failed cleanup or still-pending readers retain ownership; there is no retry or repair-success inference.

## Disabled native implementation

`WindowsSystemRepairDirectLaunchApi` and its containing backend/platform all keep literal false execution flags; production journal creation is independently false. Native methods reject before token/native access. After those guards, the adapter checks Windows64 and managed structure sizes/offsets against the reviewed definitions. Those checks are not observed Windows ABI behavior.

The private target holds the actual verified executable lease and independently binds Dism.exe or sfc.exe to the selected operation, genuine held system directory, matched embedded version and valid held hash metadata. Frame allocation and create both check this binding and trust-cleanup state. Already-effective nonimpersonated administrator rights are rechecked before creation; no UAC or alternate credentials are requested.

An explicit zero-initialized HGlobal call frame contains application, writable command, minimal sorted Unicode environment, working directory, STARTUPINFOEX and PROCESS_INFORMATION. Attribute/list allocations and preallocated raw handle slots stay rooted in the API. Both successful pipe or process outputs are saved before validation/result allocation; failed outputs are ignored. The native create callback captures actual last error only on failure. Unexpected successful sizing never reports a stale error.

Core CreateAttempted means the permit was claimed and the trusted adapter callback was entered; it is not a count of actual Win32 invocations. A failed reader/admin precheck can return known no child before that syscall, with no invented native error. Readers are rechecked after call-frame preparation immediately before the syscall; future I/O failure is still possible and no atomic cross-boundary guarantee is claimed.

Reader owners pin buffers and cache their read callbacks before worker scheduling/Ready publication. Completion is the actual worker task. TRUE/zero continues reading; documented false109 establishes EOF. Unexpected false or thrown callbacks retain bytes/pin/handle rather than assuming I/O settlement. The original process handle is polled from a background owner, separately from exit-code retrieval. Close/delete/free operations remain controlled by the kernel; no process/service kill, PID reopen, cancellation API, inheritance fallback or silent retry exists.

Exceptional post-create transitions can still retain an unmonitored original process-information packet; rooted slots/allocations do not imply every catastrophic managed failure is observed. The native source is not enabled on the strength of compilation or mocks. Actual Windows handles, ABI, inheritance, EOF, permissions, resource failures, journal namespace/durability, crash/restart reconciliation and public UI qualification remain open.
