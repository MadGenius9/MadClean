# Explicit registration postcheck after an MSI request

This workflow connects the existing selected MSI request result to the existing read-only exact-product registration reader. It does not enable the production uninstall launcher, launch another installer, refresh the global inventory, scan files or authorize deletion.

A historical target is copied only when the selected-product request preview has passed its existing exact-source preparation policy. The original product GUID, registration identity, ARP provenance, uniquely observed native context, reported display metadata and historical source coverage remain bound to that intent. Legacy scope-only previews have no postcheck target. The target stays in memory and follows the existing 24-hour watch lifetime; selection changes cannot silently retarget it.

After the same request returns an accepted actual ClientExited observation, a separate explicit button prepares a new short-lived registration-read scope. The request must have reserved dispatch and observed client creation; its result must pass the existing result policy with ordered UTC exit evidence. Optional native PID/start/code fields stay optional. Failure, cancellation or an unknown exit classification does not prevent an informative registration read and never becomes successful uninstall evidence. A consumed or expired uninstall selector is not revived. The new query must start after the observed client exit and belong to this exact postcheck scope/target.

The existing Windows reader sequentially observes the exact GUID in three supported ARP locations and current-user/machine MSI contexts. Per-source Present/Absent/Unknown and coverage retain their existing meanings. Receipt, client exit and registration absence are distinct observations: even complete registration absence cannot establish complete uninstall, exclusive ownership of leftovers, or safety of removal. Shared dependencies, user data, saves and settings remain protected. The retained application baseline is unchanged.

The App owns the actual read task and pending native work through cancellation, stale publications and presentation errors. A caller stopping its wait does not stop synchronous native calls or release their handles. New requests and normal close remain blocked until ownership settles; uncertain ownership remains retained. No query runs automatically after an uninstall or ordinary inventory.

Portable policy tests and WPF compilation can establish source/identity/time/result admission and build consistency only. They do not establish Windows Installer execution, actual registry/MSI reads, Windows permissions, WPF input/rendering/close behavior or native cancellation. Runtime qualification remains separate, and all production action gates remain unchanged.
