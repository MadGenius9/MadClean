# Selected package-family Settings review

The current-user Windows packages view now offers **Preview selected package page**, followed by a separate **Open reviewed package page** action. This requests Windows' App features / Advanced options page for the selected package family. It does not invoke an uninstall, reset, repair, termination, package activation or deployment operation. Windows controls the available page/options and any later action the user separately chooses there. The documented route does not guarantee an uninstall control.

## Official destination and source binding

The current official [Launch Windows Settings reference](https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-settings) was retrieved successfully on 2026-11-03 from its [Microsoft source](https://github.com/MicrosoftDocs/windows-dev-docs/blob/docs/hub/apps/develop/launch/launch-settings.md). Its App features row explicitly documents `ms-settings:appsfeatures-app?<PFN>`, with the bare package family name after the question mark. `?PFN=...` is not substituted. The source describes Reset, add-on/downloadable-content management and other app features; it does not promise that all apps or Windows versions offer every option.

The preview binds the actual selected object reference to one loaded current-user Main/Bundle source result received within five minutes. The preview shows that exact registration, the family-level destination, the exact URI, source coverage, source receipt/preview times, reported non-removable flag, permissions and limits. A conservative ASCII identity allowlist validates Name/FamilyName/full-identity/version/architecture relationships; this is a supported subset for navigation, not a complete Windows identity parser. Framework/resource rows, unknown type/essential identity fields, cloned selections, duplicate full identities, inconsistent families and stale/future observations cannot produce a preview. Valid Main/Bundle records sharing one family are not presented as a unique app or exact-version destination.

Opening performs one new explicit current-user metadata query through the existing fixed Appx inventory. It requires the exact selected full registration metadata still to match, preserves Available versus Partial coverage, and creates a short-lived membership-bound handoff only after that observation. The final STA dispatch boundary revalidates this typed handoff (fresh receipt within 30 seconds), the original preview and the exact authored URI. Selection highlighting alone performs no query or handoff. Changed metadata, failed/unknown coverage or absent/conflicting identity requires a new inventory and preview. Matching is not signature authentication, action eligibility, global absence or atomic continuity: Windows registrations can change after the observation.

## Cancellation, privacy and ownership

Selection, search and source changes invalidate the preview and cancel a linked attempt token. This stops queued dispatch when possible rather than only hiding stale UI results. The existing shell STA owner/pending gate is shared with generic fixed Windows handoffs; their exact catalog predicates remain unchanged. No public arbitrary-URI launcher is introduced. A pending or uncertain shell owner blocks another package read/handoff. Metadata work is awaited; the UI does not abandon its worker or force-close native state.

Cancellation before shell dispatch requests no page. After dispatch, cancellation/timeout cannot undo the request and remains Unknown where the launcher cannot establish completion. The combined workflow does not overwrite that result with a generic post-work cancellation check. A shell return, PID or null Process does not establish target-window appearance or completion of any operation in Windows. No elevation is requested by MadClean; Windows/policy can require separate permission for later actions. Closing MadClean does not cancel a page already handed to Windows.

Package names, full/family identities and exact targeted URI remain in the in-memory local preview only. Activity logging uses existing fixed operation/outcome enums, with no identity, URI, search text or provider output. Loaded-data screenshots and raw exports are not added. Ordinary inspection does not invoke this workflow, and no Settings page is automatically opened during native smoke validation.

## Validation limits

Portable boundary tests cover hostile URI delimiters/escapes/control, stale/future observations, cloned/duplicated/missing selections, changed registration metadata, conflicting family rows, Main/Bundle family-level navigation, unknown dependency/type fields and final handoff expiry. Existing exact generic Settings catalog tests must continue to pass. Linux compilation is not Windows Settings handler, current-user query/selection interaction, physical-input or page-appearance validation. Actual shell handoff and page availability remain manual Windows checks; no uninstall/reset/repair is run while building or testing.

This completes a selected supported Windows review route, not direct MadClean uninstall execution, package-removal eligibility, application ownership analysis or the later reviewed-action roadmap.
