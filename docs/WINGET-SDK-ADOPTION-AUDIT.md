# Pinned WinGet SDK adoption audit

Read-only research, 2026-11-03. This audit inspected official source and ZIP/PE metadata only. It added no dependency, project, lockfile, adapter or runtime configuration and invoked no WinGet/COM operation. It neither explains the existing text parser's `HeaderNotRecognized` result nor changes its Unknown outcome.

## Exact evidence and important version differences

The inspected package is [Microsoft.WindowsPackageManager.ComInterop 1.10.340](https://www.nuget.org/packages/Microsoft.WindowsPackageManager.ComInterop/1.10.340), retrieved from NuGet's official flat-container endpoint. Its SHA-256 is `518baecd9f691060443150f08eb1cf81f5a327ba483408a982d932682c11df77`. This digest identifies the inspected download; it is not a claim that this research verified its package signature or reproduced its binaries.

Source was read from Microsoft's exact [`v1.10.340` release tag](https://github.com/microsoft/winget-cli/tree/v1.10.340), not substituted with current master. Source-tag inspection is not proof that every installed App Installer server has that implementation. The client projection's NuGet version and the installed server's version/capabilities are independent.

Two differences from [the earlier current-source research](WINGET-STRUCTURED-DISCOVERY-RESEARCH.md) matter:

- The release-tag C# sample still references SDK 1.9.25180 and generates a projection. It is not the packaging recipe for the inspected 1.10.340 ZIP. Current master's newer sample cannot establish the older package's behavior.
- Release-tag `CatalogPackage` uses a read-only pin evaluator and `GetLatestAvailableVersionForPins` / `IsUpdate`. Current master uses a different applicability-selection helper. Therefore a version-independent UI must say **WinGet reports a newer version under this catalog's policy**, not promise installer/hardware applicability. False is never Up to date or proof the newest version is installed.

## Activation and privilege boundary

The release [out-of-process factory](https://github.com/microsoft/winget-cli/blob/v1.10.340/src/Microsoft.Management.Deployment.OutOfProc/Factory.cpp) first uses the fixed production class with `CLSCTX_LOCAL_SERVER | CLSCTX_NO_CODE_DOWNLOAD`. It does not pass `CLSCTX_ALLOW_LOWER_TRUST_REGISTRATION`. Only an already-administrator caller receiving `REGDB_E_CLASSNOTREG` enters manual activation, passing flags zero.

The release [manual activation client](https://github.com/microsoft/winget-cli/blob/v1.10.340/src/WinGetServer/WinGetServerManualActivation_Client.cpp) resolves an existing `Microsoft.DesktopAppInstaller_8wekyb3d8bbwe` package with Windows package APIs and starts its `WindowsPackageManagerServer.exe --manualActivation` under the inherited caller, then obtains the interface over local RPC. The inspected production path has no download, package installation, registration repair, runas, credential change or engine bootstrap. `Terminate` frees the RPC binding; it does not terminate the shared server process. Package absence fails rather than installing it.

Metadata inspection of the package's static x64 factory found the production PackageManager GUID and production package/server strings, with no corresponding development GUID/package/server strings. This supports the intended production build selection; string/GUID presence is not executable authentication or proof of all runtime effects.

**Do not credit this release with current master's RPC identity guarantees.** Its manual path uses an `ncacn_np` named-pipe endpoint based on user SID and contains no `RpcBindingSetAuthInfoEx` call. Current source inspected earlier uses authenticated `ncalrpc`. This audit establishes a source difference, not an exploit or vulnerability verdict. Existing administrator status is not itself an elevation request. Before adopting an inherited-admin manual path, either audit a newer exact stable package that meets the intended server-identity contract, or explicitly scope a first candidate to the release's ordinary non-elevated registered-COM path. Do not copy the internal manual-activation implementation or silently add a fallback to repair availability. The separately documented direct-COM route below has no such fallback.

## Mandatory pre-connect contract

The release [reference implementation](https://github.com/microsoft/winget-cli/blob/v1.10.340/src/Microsoft.Management.Deployment/PackageCatalogReference.cpp), [header](https://github.com/microsoft/winget-cli/blob/v1.10.340/src/Microsoft.Management.Deployment/PackageCatalogReference.h) and [IDL](https://github.com/microsoft/winget-cli/blob/v1.10.340/src/Microsoft.Management.Deployment/PackageManager.idl) establish:

1. `AcceptSourceAgreements` defaults **true**. Require actual support for contract 6 and set/read back false on every non-composite catalog reference before `Connect` / `ConnectAsync`, including every remote reference supplied to a composite. A missing setter/interface fails Unsupported before connection. Never retry with the default. The composite setter throws; configuring only the composite is insufficient.
2. Contract 10 exposes `AuthenticationInfo` and `AuthenticationArguments`. Require a known `AuthenticationType.None` for the first supported source. Unknown, missing or authentication-required catalogs remain Unsupported/Unknown before connection. If authentication arguments are constructed, use `AuthenticationMode.Silent` and no account; never Interactive or SilentPreferred. The release converter defaults null arguments to Silent, but relying on that default is unnecessary.
3. The official release [source constants](https://github.com/microsoft/winget-cli/blob/v1.10.340/src/AppInstallerRepositoryCore/SourceList.cpp) identify name `winget`, type `Microsoft.PreIndexed.Package`, argument `https://cdn.winget.microsoft.com/cache`, identifier `Microsoft.Winget.Source_8wekyb3d8bbwe`. Read bounded structured `Info` and require the explicitly supported tuple, not name alone. Preserve Origin/TrustLevel as separate provider metadata; do not turn a matching name or URL into independent publisher authentication. Do not add/reset/edit sources or supply headers, tokens or credentials.
4. `ConnectResult.Status` must be Ok and provide a catalog; `FindPackagesResult.Status` must be Ok. Agreement rejection, capability denial, source access, partial property failures and unrecognized enums retain their actual unsuccessful coverage. Never interpret an empty/failed query as no updates.

Property support must be established against the actual returned object/server, not inferred from the client assembly merely declaring a newer interface. Agreement/authentication getters use source information and may themselves fail; those failures cannot lead to a connection with defaults.

## Smallest useful query and projection

Use two explicit scopes. Local inventory can connect `GetLocalPackageCatalog(InstalledPackages)` after the non-composite pre-connect rules. Online discovery can resolve the one existing supported official catalog with `GetPackageCatalogByName`, then use `CreateCompositePackageCatalogOptions` with only that reference and `CompositeSearchBehavior.LocalCatalogs`. The release [converter](https://github.com/microsoft/winget-cli/blob/v1.10.340/src/Microsoft.Management.Deployment/Converters.cpp) maps LocalCatalogs to installed-first correlation; [Connect](https://github.com/microsoft/winget-cli/blob/v1.10.340/src/Microsoft.Management.Deployment/PackageCatalogReference.cpp) combines the selected remote source with the installed source. Do not search every remote package or silently use all configured sources.

Set a nonzero bounded `FindPackagesOptions.ResultLimit` and preserve `WasLimitExceeded`. There is no pagination token in the public IDL. Bound the number and length of projected records even after the native limit. Read only the needed Id, Name, installed/version fields, the provider's update Boolean and separately observed default offered version/source. Do not request uninstall-command, installation-path or other metadata fields merely because `GetMetadata` exposes them. Log fixed statuses/counts/HRESULTs only, not package identifiers or raw provider messages.

[AvailableVersions](https://github.com/microsoft/winget-cli/blob/v1.10.340/src/Microsoft.Management.Deployment/CatalogPackage.cpp) has explicitly unspecified ordering. Never choose its first element as latest or compare arbitrary package versions using lexical ordering/System.Version. Missing installed correlation, a missing offered version, an unknown comparison or property exception remains Unknown/Partial. `DefaultInstallVersion` and `IsUpdateAvailable` are observed facts, not installation permission, compatibility, security or universal coverage.

Online Connect may refresh/download catalog metadata and write provider-owned caches/logs. `InstalledPackageInformationOnly=true` explicitly avoids external resources and is not a fresh available-update check. Setting `PackageCatalogBackgroundUpdateInterval=0` suppresses its background update check, but does not prove all source information is fresh or that initial Open needs no remote resource. Record request/result time separately from `Info.LastUpdateTime` and unknown data age.

## Cancellation and ownership

The release's `ConnectAsync` calls synchronous Connect; [FindPackagesAsync](https://github.com/microsoft/winget-cli/blob/v1.10.340/src/Microsoft.Management.Deployment/PackageCatalog.cpp) resumes in the background then calls synchronous FindPackages. Those bodies do not provide a documented servicing-style owned cancellation lifecycle. Cancelling a projected task or reaching a caller deadline does not establish that source/service work stopped.

Use one rooted query owner registered before scheduling, with bounded caller wait and retained native operation/object references until the actual owner finishes. A cancelled/timed-out caller cannot force-close another worker or kill the shared WinGet server. Avoid `Marshal.FinalReleaseComObject` on projected/shared WinRT wrappers. Describe actual request completion independently from provider background work; do not invent a checked native reference-count/release result that the projection does not expose. Exact projected-object/operation disposal behavior still needs review and Windows testing.

## Build and single-file packaging requirements

The ZIP includes `lib/net8.0-windows10.0.22000.0/Microsoft.Management.Deployment.CsWinRTProjection.dll`, a WinMD, and static/dynamic native factories for x64/x86/ARM64. It declares no NuGet dependencies. Embedded type metadata refers to `WinRT.Runtime, Version=2.1.0.0`; the package's absence of dependencies is not proof that the application can omit the C#/WinRT runtime. Resolve an explicit supported C#/WinRT package graph deliberately and lock it; do not copy isolated DLLs from the research folder.

The shipped `.targets` default `MicrosoftManagementDeployment-FactoryLinkage` to static, reject unspecified AnyCPU, select native architecture from RuntimeIdentifier/Platform, and add the WinMD and native DLL to `ReferenceCopyLocalPaths`. For MadClean, keep the first candidate Windows 11 x64 and explicitly select x64 for ordinary builds as well as publish. The existing Windows-targeted projects would need a compatible Windows 22000+ target before referencing this package. Core remains portable. This is a deliberate target/dependency/lockfile change, not a restore side effect.

PE import inspection of the static x64 factory found OS libraries; the dynamic variant also imports MSVCP140/VCRUNTIME140 variants. For the SDK default-factory route, the static variant avoids that additional VC++ runtime dependency; the completed direct-COM choice below omits both native variants entirely. This is metadata evidence, not a Windows load test.

Current single-file properties do not by themselves qualify SDK loading: targets copy the factory as an ordinary local reference, and the activation loader's DLL resolution must work from the actual bundled/extracted layout. First verify the complete published folder, then the requested single-file layout with the real user-triggered SDK path. Neutral executable startup alone never loads a lazy provider and cannot prove its native dependency works. Do not quietly drop a required sidecar while claiming a standalone executable is complete.

## Adoption recommendation and finite remaining gates

Do not add 1.10.340 blindly from the master sample. A small maintainable adapter is feasible using the official projection, a narrow Core typed-projection policy and one lazy Windows query owner. Before coding, choose the exact stable activation/version contract (especially the inherited-admin path), the explicit C#/WinRT/Windows-target package graph, and a verified publication layout. Then test missing agreement control, authentication uncertainty, source mismatch, failed Connect/Find, truncation, missing versions, false update/pins and caller cancellation in portable policy tests; qualify actual Windows query and published loading in the existing separate update-discovery job without accepting agreements, bootstrapping or installing software.

The present audit does not qualify Windows activation, source authentication, query results, release safety or the executable's SDK loading. The old text adapter remains unchanged and honestly Unknown where its existing parser cannot qualify output.


## Completed direct-COM adoption choice

A first implementation can deliberately use **ComInterop 1.10.340's prebuilt Windows 22000 projection, Microsoft.Windows.CsWinRT 2.2.0's runtime, and `MicrosoftManagementDeployment-FactoryLinkage=none`**, with a small MadClean-owned fixed-class COM factory. This is a concrete supported interop route, not a reason to copy the SDK's internal `LocalServerInstanceInitializer`. Microsoft's [exact-release C++ out-of-process sample](https://github.com/microsoft/winget-cli/blob/v1.29.380/samples/MinimalCallers/C%2B%2B/WinGet-OutOfProc/WinGet-OutOfProc.cpp) and [COM API specification](https://github.com/microsoft/winget-cli/blob/v1.29.380/doc/specs/%23888%20-%20Com%20Api.md) explicitly use/require `CoCreateInstance` for these objects. The locally retrieved official sample contains production CLSIDs PackageManager `C53A4F16-787E-42A4-B304-29EFFB4BF597` and FindPackagesOptions `572DED96-9C60-4526-8F92-EE7D91D38C1A`. Each additional required options class must be matched to its published production CLSID before being added to the factory's private allowlist.

The factory should select only `CLSCTX_LOCAL_SERVER | CLSCTX_NO_CODE_DOWNLOAD`, request the standard WinRT IInspectable interface, and fail Unavailable on unsuccessful existing-registration activation. It must have no arbitrary CLSID input, development CLSID, lower-trust option, manual RPC activation, SDK default-constructor fallback, package/engine download, registration repair or elevation request. Every projected object that needs creation, including find/composite/authentication options, must use this factory; `new PackageManager()` or `new FindPackagesOptions()` would reintroduce a different activation path.

The package's shipped common targets explicitly accept linkage `none`, omit either native factory DLL in that case, and mark the WinMD `IsOutOfProcess=true`. This removes the native SDK-factory loading requirement; it does not itself prove a working project/package graph. Select the prebuilt projection deliberately, avoid accidental duplicate projection generation, and obtain the runtime from a pinned normal package reference rather than copying research DLLs. A viable build must explicitly resolve its Windows 22000+ target and runtime/reference graph, then lock and qualify it with the real adapter. The WinMD's copy/output settings and any C#/WinRT build-asset exclusions must be verified by that build, not inferred from this document.

### Public wrapping and reference ownership

Exact C#/WinRT source was located through official tag `2.2.0.241111.1`, commit **8649ee3eeb2445ca2a36d80d878ef60b96a6c65d**. Its [interop guide](https://github.com/microsoft/CsWinRT/blob/8649ee3eeb2445ca2a36d80d878ef60b96a6c65d/docs/interop.md#create-rcw) explicitly documents `MarshalInspectable<T>.FromAbi(ptr)` as a replacement for legacy RCW creation. The [exact source](https://github.com/microsoft/CsWinRT/blob/8649ee3eeb2445ca2a36d80d878ef60b96a6c65d/src/WinRT.Runtime/Marshalers.cs) confirms that class and method are public in the normal non-EMBED runtime. `FromAbi` does not consume the original `CoCreateInstance` pointer; it queries/relinquishes its own temporary IUnknown and returns a projected RCW. Release the factory's one acquired raw reference in a finally block using the complementary public `MarshalInspectable<T>.DisposeAbi(ptr)` (or an equivalent documented balance), including wrapping failures. Do not call CLR `GetObjectForIUnknown`, cast a raw `__ComObject`, or implement application reflection over private projection constructors.

The runtime's [exact RCW implementation](https://github.com/microsoft/CsWinRT/blob/8649ee3eeb2445ca2a36d80d878ef60b96a6c65d/src/WinRT.Runtime/ComWrappersSupport.net5.cs) uses `GetOrCreateObjectForComInstance` and may return a cached wrapper. Keep all projected objects/operations strongly reachable until the actual asynchronous query has returned and primitive projection is complete. Do not force `Marshal.FinalReleaseComObject` or dispose `((IWinRTObject)obj).NativeObject` as though that cached wrapper were exclusively owned. The [ObjectReference implementation](https://github.com/microsoft/CsWinRT/blob/8649ee3eeb2445ca2a36d80d878ef60b96a6c65d/src/WinRT.Runtime/ObjectReference.cs) confirms that `FromAbi` adds a reference while `Attach` transfers one; generic overloads include obsolete variants, so the direct public marshaler route is preferable here. Normal RCW lifetime is managed by the runtime. Releasing the factory's reference or finishing a client call is not proof that all server references/background work ended. No application ownership diagnostic should claim zero native references or a stopped shared WinGet server.

Metadata-only inspection of the actual 1.10.340 projection found `<Module>..cctor` calling `WinRT.ProjectionInitializer.InitalizeProjection`. Its 21-byte method calls GetTypeFromHandle, get_Assembly and RegisterProjectionAssembly. The exact C#/WinRT [registration method](https://github.com/microsoft/CsWinRT/blob/8649ee3eeb2445ca2a36d80d878ef60b96a6c65d/src/WinRT.Runtime/TypeNameSupport.cs) only adds the assembly to the projection assembly list. No WinGet activation was found in that module initializer. This is bounded metadata/source inspection, not execution or proof of all possible future type initialization; the adapter must still keep all factory/object creation inside the explicit user-triggered query.

The inspected runtime package SHA-256 is `a89df04f86c1671fcf30ccd6f5cc78eb189a29daa19f3d92d00987d4b3fc3b63`. The current newest stable SDK inspected, **1.29.380**, still uses the older named-pipe manual path and targets Windows 26100; its package digest is `09656d66cf4f5d101ea4ed3fedb0733ca76fa224dfe6ad758be247903e9de696`. Merely choosing the newest stable package does not establish that current master's authenticated ncalrpc implementation has shipped. Direct registered COM with no fallback avoids depending on that unaudited manual path, at the honest cost of Unavailable on hosts/callers whose registration cannot activate.

### Remaining finite qualification

The supported choice above is sufficient to begin a small adapter without another activation-research round. It is **not** a claim that the package graph or Windows behavior was tested. Before production use, build the explicit prebuilt-projection/runtime graph on the supported SDK, enforce the existing pre-connect agreement/authentication/source rules and bounded primitive projection, then test real registered activation/query and the actual published layout. No native SDK factory is needed in this route, but real single-file loading of managed projections, runtime metadata and any remaining WinMD output still requires an adapter-triggering packaged test. Keep trimming/AOT disabled for the current WPF/reflection-dependent stack. A missing COM registration/interface remains Unavailable/Unsupported with no repair or fallback; a false update Boolean remains a limited catalog observation, never Up to date.


### Exact unbuilt consumer-property candidate

Inspection of the actual CsWinRT 2.2.0 package's `build/Microsoft.Windows.CsWinRT.targets` confirms `CsWinRTEnabled` and `CsWinRTGenerateProjection` are public build switches. For a consumer of the prebuilt projection, begin with the following deliberate properties (and normal pinned package references to ComInterop 1.10.340 and Microsoft.Windows.CsWinRT 2.2.0):

```xml
<TargetFramework>net10.0-windows10.0.22000.0</TargetFramework>
<PlatformTarget>x64</PlatformTarget>
<MicrosoftManagementDeployment-FactoryLinkage>none</MicrosoftManagementDeployment-FactoryLinkage>
<MicrosoftManagementDeployment-OutputWinMD>false</MicrosoftManagementDeployment-OutputWinMD>
<CsWinRTEnabled>false</CsWinRTEnabled>
<CsWinRTGenerateProjection>false</CsWinRTGenerateProjection>
<CsWinRTAotOptimizerEnabled>false</CsWinRTAotOptimizerEnabled>
<PublishTrimmed>false</PublishTrimmed>
```

Do not enable `CsWinRTEmbedded`, `CsWinRTComponent`, NativeAOT or a namespace include that regenerates SDK types. Disabling projection avoids a duplicate projection of types already supplied by the package. Keep the CsWinRT build targets imported rather than blindly excluding all build assets: its unconditional `CsWinRTRemoveWinMDReferences` target removes raw `.winmd` references/copy/dependency entries to prevent NETSDK1130, even when projection is disabled. `FactoryLinkage=none` itself makes the SDK's unspecified-platform error inapplicable and omits native factory DLL copying; x64 is the chosen product/runtime scope rather than a claimed SDK requirement in this configuration. `OutputWinMD=false` is a proposed publication choice requiring actual packaged-query verification, not a demonstrated runtime result.

Any projects referencing the higher Windows-targeted integration must use a compatible target. Keep Core and its tests platform independent. A successful restore/build must still verify the selected managed runtime version and actual output/deps graph; these properties have been read from the exact package but were not built in this research. The finite next step is implementation/build and Windows qualification, not another generic API search.
