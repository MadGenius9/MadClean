# Published executable startup validation

This development check publishes the existing WPF project as a self-contained Windows x64 single-file app, using the README options and locked runtime package graph. It is separate from distribution packaging: no ZIP, binary upload, signing, installation or release is performed. Compilation alone never satisfies this check.

The Windows preparation script accepts no arguments. It creates a fresh marked scope under artifacts, refuses stale descriptors, validates bounded ordinary files, and writes an exclusive three-field descriptor bound to the current source commit. The publish output and initially empty bundle cache stay outside the uploaded validation directory. Fixed CI logs retain only bounded scrubbed development output.

After prior GUI/native workers and their owned tree teardown settle, the harness validates the descriptor, retains native leases on its own executable and directory ancestors, and starts that exact executable without arguments or shell execution. The child receives only selected standard Windows environment variables plus its owned bundle extraction directory; CI credentials, startup hooks and profiler variables are not inherited. There is no production test flag or permission override.

Out-of-process UI Automation reads only this own process's window and neutral Overview controls. It checks unchecked summaries, unknown Defender status, absent capacity reading and no selected drive twice. It invokes no inspection, update, navigation or inventory command and takes no capture. These properties establish only the observed neutral dashboard; they do not trace every I/O operation or prove the absence of background behavior in all environments.

Using the held own process handle, a fixed-capacity Windows module query observes the owned process image and runtime form. The dynamic route requires coreclr.dll under the owned extraction cache. The separately qualified .NET10 static-host route below accounts for CoreCLR linked into the apphost. Unavailable or truncated module information stays inconclusive; a successful launch alone is not substituted for runtime-form evidence. Raw module names and paths are never exported. A graceful close request is followed by actual process exit and exit-code observation. A queued WM_CLOSE alone is not completion. An observed exit before the required window or an observed nonzero exit code fails this startup contract; no crash cause is inferred.

Caller cancellation or deadline cannot release another worker's process/native resources. Unsettled workers, ambiguous launch outcomes or cleanup uncertainty retain the scope. Only after actual child exit and returned Automation calls may bounded marker/identity/tree validation and checked lease release precede owned development artifact removal. There is no force-kill or cleanup of client files.

The required source-bound published-executable-startup result exports bounded states and booleans only. Linux compilation and preparation tests with a fake publisher are not Windows startup evidence. A passing runner observation would still leave physical input, DPI, assistive technology, signature/reputation, every supported Windows configuration and action-module validation outstanding.

## .NET10 static runtime host

The earlier runtime assertion incorrectly required a separate coreclr.dll. Actual source4223e44/run41482324417 (evidencea6cfb703aee3a00ef5be8f744c4595f90421539a) returned own-bundled-runtime-unobserved and therefore did not assess its new UIA peer. Launch, own window, exit 0 and owned cleanup were observed; no neutral or runtime proof is inferred.

Fresh official .NET10 source supports another hosting form: [Windows singlefilehost linkage](https://raw.githubusercontent.com/dotnet/runtime/release/10.0/src/native/corehost/apphost/static/CMakeLists.txt) includes coreclr_static; [its CoreCLR resolver](https://raw.githubusercontent.com/dotnet/runtime/release/10.0/src/native/corehost/hostpolicy/static/coreclr_resolver.cpp) binds functions directly instead of loading a CoreCLR DLL. The absence of that DLL neither proves nor disproves self-contained execution. This corrects the fixture's assumption; it does not promote the earlier result.

The new fixture-only portable metadata reader uses the same already-leased owned executable, not LoadLibrary, an export invocation or remote process memory. It recognizes the six fixed [static-host exports](https://raw.githubusercontent.com/dotnet/runtime/release/10.0/src/native/corehost/apphost/static/singlefilehost.def), including the explicit ordinals2/3/4, and the exact112-byte [RuntimeInfo layout](https://raw.githubusercontent.com/dotnet/runtime/release/10.0/src/coreclr/debug/inc/runtimeinfo.h). The signature, schema2 and runtime10.0 version fields must match. Unspecified alignment padding and symbol-index payloads are not interpreted as trust. PE architecture, RVA/file mappings, duplicates, forwarders, section/table/string/read budgets and stream-position restoration are validated. No whole image/section is loaded, and changed or unsupported formats remain unqualified. Tests use inert metadata that is never executed. The reader is linked into portable tests and the development harness; it is not shipped in Core or the app.

Static metadata alone establishes neither execution nor authenticity. Acceptance also requires a complete bounded module snapshot with all paths returned, an actual own-apphost module path bound to the already-held/bookended executable, no observed foreign CoreCLR module, and genuine neutral managed UI in that same retained own process. A partial snapshot or foreign CoreCLR never switches to static acceptance. Read leases and owned-scope identity bookends do not claim cryptographic equality with mapped process memory or hostile-user namespace protection. The final startup result still requires both runtime and neutral UI observations, actual normal exit and confirmed owned cleanup. Returned unavailability of one independent observation is recorded with its own stage/error while the other may proceed only after live-process/window/retention/cancellation guards; invariant failures, cancellation and ownership uncertainty stop continuation. Raw module paths, exports and bytes are not published. The source-bound result below qualifies this route on the disposable CI host; changed formats and other Windows environments remain separate checks.


The final borrowed-stream boundary restores the reader's logical position, disposes its unowned wrapper, then explicitly restores and reads back the original native cursor before releasing the handle pin. A buffered FileStream may legitimately have a different intermediate native cursor; that intermediate state is not a failure. Any actual final restore/readback uncertainty retains ownership and blocks acceptance/continuation. Independent review found no remaining static blocker. Full local build passes with zero warnings/errors and all 1,230 portable tests pass, including 35 new inert metadata boundary cases; the unchanged Python suite was last 152 total / 151 passed / one Windows-only skip. The actual Windows result below records the static-host and independent UI observations.
