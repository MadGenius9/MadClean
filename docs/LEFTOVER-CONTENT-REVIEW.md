# Selected leftover directory metadata review

This separately selected module previews filenames and known logical sizes under one previously recorded install directory. It never reads file contents or deletes, renames, uninstalls, adds a cleaner target, executes a command or changes permissions. Registration disappearance does not prove uninstall completed; a surviving directory is not proven junk. Unknown ownership and active use remain explicit even when metadata can be read.

## Portable scope validation

`LeftoverContentReview.ValidateScope(candidate, before, after, now, token)` takes an existing `LeftoverCandidate` and complete `CheckResult<InstalledApplication>` baseline/refreshed ARP snapshots. Both must be Available and bounded to 20,000 entries. Every identity must be valid and unique case-insensitively, including unrelated entries; the selected prior identity must exist exactly once and be absent after refresh. The candidate's normalized local path must exactly match its prior recorded install directory. No broader root, substitute path, current app's replacement install path, UNC/device/environment-expanded path or freeform “safe” caution authorizes traversal. Validation performs no filesystem probe.

Protected user/profile/data/save/settings/credential/system/shared paths and broad installation roots are blocked by typed path policy. Any equal, ancestor or descendant overlap with another prior or current app's supported recorded install root blocks the scope. String-prefix neighbors are distinguished from actual directory overlap. The supplied caution/evidence is retained as source uncertainty and is never interpreted as authority or used to override policy.

Available ARP coverage is not all software or all install directories. Missing/unsupported other install locations are counted and disclosed, alongside portable/unregistered/packaged-software gaps. No known overlap is not proof of exclusive ownership. The root UI refreshes real ARP inventory immediately before validation; the earlier explicit in-memory baseline can remain older by design. `ValidatedUtc` describes this scope validation only. Snapshot models have no inventory timestamp, so the validator invents no snapshot-age claim.

Only the factory can normally construct the immutable `LeftoverContentScope`; it is not an execution authorization or a security boundary against a malicious same-user process/reflection. It contains `RootPath`, `RegistrationIdentity`, `ValidatedUtc`, original source evidence/caution and ownership coverage. Windows must recheck scope freshness (two-minute product-policy limit), actual root existence, local volume, ancestry and native identity before metadata enumeration. A qualified portable scope does not establish filesystem safety or existence.

## Metadata report and limits

`ILeftoverContentInventory.PreviewAsync(scope, token)` returns `CheckResult<LeftoverContentReport>`. Each entry has a path, directory flag, nullable known logical byte count, bounded native identity metadata and `ActiveUse = "Unknown"`. Directories do not acquire invented byte totals. Native file identity is metadata, not application ownership or deletion authorization. Coverage is an explicit string list, with bounded path-specific issues, visited counts and truncation.

Limits are 128 files, 128 directories, depth eight and 256 issues. The native adapter must remain beneath the selected root, revalidate enumeration observations through safe native handles and avoid reparse points, offline/cloud recall, unsafe/encrypted/protected/system paths and observable locks/access denial. Root-to-leaf fixed-local guards and no-follow child identity checks belong to the Windows adapter; portable syntax checks do not replace them. Metadata-only rights cannot strictly establish inactivity. Observable locked/inaccessible paths are skipped, while every displayed item's active-use state remains Unknown. No item becomes action-eligible.

`LeftoverContentPolicy.IsProtectedDescendant` accepts one path component only. It rejects separators, traversal, ambiguous names, device names and protected user/profile/data/save/settings/credential/system/shared directory names (including browser-profile patterns). It conservatively excludes common configuration, database, certificate/key, save, backup, document and media extensions from file metadata preview. These are deliberate default exclusions, not a complete content classifier or a guarantee that other files contain no user information. No extension, directory name or size proves safe removal; no content is inspected. The adapter may impose further native protections.

## Validation and remaining work

Refreshing registrations invalidates the previous candidate list and its absence claims; an existing complete baseline may be retained for a new comparison. The selected-content flow retains its candidate only as explicitly labeled historical evidence while refreshing registrations and validating its exact scope again. Installed-app row publication has a separate incomplete state: cancellation/failure clears partly published rows and cannot leave an older complete status attached to a new partial list. A subsequent folder-preview failure does not invalidate an already completed registration inventory.

Portable tests cover incomplete snapshots, missing/still-present/duplicate selected identities, exact-path substitution and widening, protected paths despite misleading cautions, all known-root overlap directions, neighboring path prefixes, unknown ownership coverage, descendant exclusions, malformed names, bounds and cancellation. They do not validate Windows handles, local volumes, path races, active-use status or GUI rendering. Native validation and full builds are coordinated separately; synthetic registrations and identity strings are test fixtures, not production inventory.

This metadata preview is not reviewed deletion. A future action would need a separate explicit scope and evidence review, actual complete candidate/retained-data protections, final identity revalidation and supported bounded action/recovery semantics. It must never infer that shared dependencies, user data, saves, settings or unknown-owned files are safe to remove. Restore points do not recover deleted files. No deletion executor is introduced here.

## Current selection and response scope

The App accepts only an exact candidate reference from the current in-session review. Selecting a different candidate invalidates its metadata view. File/folder detail selection likewise requires an exact current row, so an equal-valued or stale reference cannot supply current details.

The metadata view distinguishes app request, registration-response receipt, scope-validation time and metadata-adapter response receipt. Those stages are not baseline capture time, a native-worker completion guarantee, proof of an uninstall or evidence of exclusive ownership. Clearing or interrupting a current attempt removes its current scope and results. Completed stages from that same attempt retain historical timestamps, including a successfully published registration inventory; an interruption does not undo them or make them an accepted file report. A new attempt/selection clears prior-attempt times. A late response/error for a replaced candidate cannot overwrite the newly selected view; any required installed-inventory publication cleanup still completes independently.

Before showing a returned report, `LeftoverContentEvidence.IsConsistent` checks its positive singleton state, exact normalized root, separator-bounded child paths, unique accepted paths, bounded counters/collections and file/directory metadata shape. Available cannot carry hidden truncation/issues; Partial stays Partial. Excluded issue paths are warnings, not accepted file entries, and may describe protected or malformed names under the scope. This is a pure lexical/data-consistency check on returned metadata, not a filesystem probe, native identity verification or permission to remove anything.

No new path crawl, content read, uninstall, deletion, registry write, elevation or native cancellation is added. A pending native worker keeps its existing ownership even when the caller stops waiting. Windows rendering and real selection-change/cancellation interactions remain unverified for local changes while GitHub pushes are paused.
