# Cooperating diagnostic admission

The selected DISM recorded-flags and fresh-scan routes now share one in-process admission capability with the dormant SFC verification candidate. This prevents cooperating routes/instances inside this MadClean process from preparing overlapping servicing clients. The legacy executor remains disabled and does not participate. There is no cross-process mutex, persistent running-state proof, recovery journal, OS servicing lock, permission grant or health result. Other programs and another MadClean process are outside this scope.

`SystemToolAdmissionGate` accepts only nonempty request IDs and the three fixed non-repair operation kinds. It admits one exact lease reference without queuing. A duplicate request GUID cannot steal the slot. The actual owner calls `Complete(true)` only after its process, streams, cancellation resources, trusted executable leases and fixture proof have actually settled. The first completion is terminal. `Complete(false)` permanently retains this gate, even if a later stale callback says true; there is no reset, disposal/finalizer release, cancellation release or override.

The single Windows facade supplies this same gate to every cooperating provider instance. Admission follows managed owner/task/capacity allocation but precedes proof transfer, worker scheduling and native work. A refused proof transfer releases only the newly acquired, never-dispatched slot; uncertain proof ownership is rooted and retained. Failure to schedule completes according to actual proof cleanup. Existing native stop/stream/host ownership semantics are preserved. Provider pending/retention properties include the shared slot.

SFC's immutable false production boundary still precedes this admission and all actual Windows work. Adding a shared capability does not enable it. Legacy integration, cross-process/recovery design, actual SFC qualification and its public confirmation workflow remain separate gates. The existing selected DISM workflows require regression evidence for this changed source; older runtime passes are not silently reused.

Portable tests exercise mixed-route concurrent admission, repairs/unknown kinds/empty IDs, terminal uncertainty, stale callbacks, GUID reuse and separate-instance scope. The passive Windows composition check holds only a managed development capability, verifies actual provider pending/retention projections and competing admission refusal, then releases its own capabilities. It never calls an enabled DISM route merely to test rejection: a guard regression must not start servicing from passive validation. No native operation is invoked by this composition check.
