# Official Surface published firmware history

This read-only Update Center addition retrieves official published release observations after an explicit user action. It does not compare the installed BIOS string, decide whether a release applies to the device, install anything or claim “Up to date.” Ordinary local inspection never invokes this network check.

## Current coverage and official sources

The adapter currently supports only the exact identity **Microsoft Corporation / Surface Laptop 6 for Business / Surface_Laptop_6_for_Business_2035**. The current Microsoft System SKU row must confirm the 15-inch product label, and the current history article must explicitly list the 15-inch device in its authored Applies To section. OEM/retail board resemblance, a similar product name and an incomplete identity cannot qualify this adapter. Firmware-reported board/BIOS fields are not used to infer applicability.

The 2033 SKU remains **Unknown** without sending requests: Microsoft's SKU reference says 13.5-inch, while the history's applicability list says 13 inch. MadClean does not round these labels or infer an exact variant mapping. Other identities are Unsupported and send no requests. These conservative results do not mean the manufacturer publishes no updates.

Only two fixed HTTPS documents are fetched:

- [Surface System SKU reference](https://learn.microsoft.com/en-us/surface/surface-system-sku-reference)
- [Surface Laptop 6 for Business update history](https://support.microsoft.com/en-us/surface/updates/surface-laptop-6-for-business-update-history)

The history URL was located through Microsoft's current [driver/firmware management documentation](https://learn.microsoft.com/en-us/surface/manage-surface-driver-and-firmware-updates), [download information article](https://support.microsoft.com/en-us/surface/drivers-firmware/download-drivers-and-firmware-for-surface) and [update-history index](https://support.microsoft.com/en-us/surface/updates/surface-update-history). Those references establish discovery provenance; the runtime client fetches only the two pinned documents, without following any links.

The article is a family history. It says updates are staged and components depend on device configuration. Each observation retains its publication date, scoped source section, source retrieval time, bounded release-note text and optional explicitly published **Surface UEFI package version**. Release-note text is the manufacturer's published description, not an independently measured repair/security/performance outcome. A release can contain drivers only. No UEFI row means the version for that observation is unknown; it does not establish absence of firmware, the latest applicable firmware, or the condition of installed software.

The client does not collect or transmit serial numbers, UUIDs, service tags, BIOS values, manufacturer/model/SKU parameters or any other inventory. The two requests use the same public URLs for every supported invocation. No firmware package, recovery image, PDF, media, scripts, tools or linked pages are fetched.

## Implementation boundary

Portable contracts, parser and transport live in `SurfaceFirmwareHistory*.cs` in Core. `IFirmwareReleaseHistory.CheckAsync(FirmwareIdentity, CancellationToken)` returns `CheckResult<SurfaceFirmwareHistoryReport>`; the report supplies published releases, scope/uncertainty and actual check time. `SurfaceFirmwareHistoryInventory` in Windows is a disposable wrapper over the locked default client. No source URL can be configured. `SurfaceFirmwareHistorySources.IsTrustedHistoryUri` exposes the exact browser-source allowlist; it rejects arbitrary paths, credentials, query, fragment, escapes and ambiguous URIs.

The default transport disables redirects, cookies and default credentials, retains ordinary TLS verification, permits 15 seconds per document and 30 seconds for the full sequence including parsing, limits headers to 32 KiB and limits each decoded UTF-8 HTML body to 512 KiB. It requires exact HTTP 200 and checks the actual response URI, content type and charset; even valid-looking HTML returned as partial content is rejected. Caller cancellation propagates. Redirects/access denial/missing/rate limits are Unavailable; offline/server/timeout/partial-response failures are Failed; unsupported, malformed or changed evidence is Unknown. None returns partial releases or a current-version verdict. Raw provider exception text is not displayed or logged.

The parser reuses the existing bounded, non-rendering article tokenizer. It requires a unique authored main/title, the exact live SKU row, exact Applies To entries, the authored `learnArticleContent` body, the specific improvements h2 section, consistent month headings, individually dated release blocks and one correctly shaped component table per release. It checks descending distinct calendar dates, rejects future dates, and supports at most 64 releases, 128 component rows per release and 4,096 characters of release-note text. Historical package versions are accepted only from a unique exact `Surface UEFI - Firmware` row with the documented legacy or current version notation; other component versions never become a BIOS version. Changed/ambiguous content fails closed. Navigation, scripts, templates and explicitly hidden elements cannot provide evidence. This is deliberately narrow authored-source parsing, not a general browser or search engine.

Both source responses must be unique, pinned and retrieved within the current two-minute sequence-consistency window; that window is a MadClean parsing rule, not manufacturer document expiry. No bundled historical fixture is shown as live production evidence. A successful check means the current source structure qualified **published family history**, not exact revision/configuration compatibility or a Windows Update applicability result. Installed BIOS identity, WUA offerings and this manufacturer history remain separate evidence.

## Precautions and future work

The displayed reminder directs the user to current official prerequisites, required power, backups and recovery-key availability when device encryption/BitLocker applies. This adapter has not established a complete model-specific power/recovery procedure. The official history warns that firmware cannot be uninstalled or reverted and that a restart may be required; retrieving that warning does not authorize a restart. Read the entire current guidance and verify the precise hardware/configuration before any later selected action. No encryption changes, flashing, downloads, installation, elevation or purchases are implemented here.

Exact installed-to-published version namespaces/comparison, OS/configuration applicability, a validated 2033 variant association, additional OEM coverage and any firmware installation remain separate roadmap work. No generic BIOS ordering or automatic flashing is planned.

## Validation evidence and limits

On Linux, an isolated .NET 10 test project compiled these portable files directly without changing shared build outputs: **41 passed, 0 failed, 0 skipped**. Cases cover driver-only latest releases, multiple releases in a month, explicit legacy/current UEFI notation, exact identity and 2033 ambiguity, source/variant/title/section/table changes, malformed and oversized content, future/duplicate/mismatched dates, malformed versions, hidden/script-only evidence, fresh unique pinned sources, fixed request privacy, URI ambiguity, no redirects/assets, access/server/offline/valid-looking partial-response failures, invalid UTF-8/content type/origin/size and cancellation. Synthetic source fixtures prove contract handling, not live hardware compatibility.

A separate locked-default-client source probe used an explicitly labelled **known catalog development identity**, without querying a PC. At **2026-10-27T11:00:31.6736232Z**, both official sources passed the authored parser and returned **23** published release observations. The newest was October 22, 2026 with no UEFI row; the August 6, 2026 release explicitly listed UEFI package `23.105.143.0`. Those are observations of the current documentation, not proof that either release applies to any user's device. The developer-only JSON is `/tmp/madclean-firmware-history-live-probe.json`; it is not bundled into the app. This probe does not validate Windows CIM, the user's hardware, live Windows Update, installation, BIOS compatibility or Windows UI rendering. The coordinator owns full solution/Windows CI validation.
