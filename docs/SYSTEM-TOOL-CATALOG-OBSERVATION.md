# Held-file Windows-tool catalog verification

This slice implements a bounded catalog identity path for the fixed OS DISM/SFC files. Following positive isolated Windows evidence, production identity can try it only after the exact direct-file trust result TRUST_E_NOSIGNATURE (0x800B0100). Other trust, signer, revocation and metadata failures never trigger fallback. It is not an integrity check or an execution feature; held-byte version checks and the immutable disabled launch gate remain. No catalog is installed, added, removed or downloaded; no servicing command, elevation or restart occurs.

The standalone development observer accepts only an existing fixed operation descriptor and opens its fixed executable through the existing read-only guards. Production ReadHeld borrows the exact existing read-leased FileStream used by the direct verifier, independently compares the supplied system directory to Windows, and validates the same handle against the derived fixed filename under its own ancestry leases. It never reopens a replacement member by path or disposes the caller stream. It retains the file handle and resets its stream before native subject hashing and SIP lookup. SHA-256 catalog hashing uses CryptCATAdminCalcHashFromFileHandle2 with an explicit SHA256 administrator context. It is separate from the ordinary whole-file fingerprint. CryptSIPRetrieveSubjectGuid receives both the same fixed filename and held handle; no undocumented NULL filename behavior is assumed.

Only the first catalog candidate returned by the installed catalog database is considered. Its path must be a canonical .cat descendant of the OS System32 CatRoot directory, with bounded path, fixed local drive, no reparse/offline/encrypted/recall objects and read-leased ancestors/file. Catalog size is at most16 MiB. It is opened existing-only, with no create/add flags. Unsupported paths and missing candidates remain Unknown; this is not a complete installed-catalog search.

At most4096 members are inspected. The first candidate with the same SIP subject GUID, exact SHA256 OID, valid algorithm parameters and identical32-byte catalog digest supplies its actual bounded reference tag. The observer never constructs a tag from a presumed hash convention. Native member data is borrowed and never freed by MadClean; required fields are copied while their catalog remains open. NULL enumeration results or limits cannot establish absence or successful database completion. Other matches need not be proven absent: the claim is existential for the selected binding, not uniqueness or exhaustive coverage.

A matching digest is not trust. Final WinVerifyTrust uses CHOICE_CATALOG, the copied actual tag, same held member file/path, same calculated subject hash and matching SHA256 administrator context. Only native LONG zero followed by the existing exact Microsoft signer predicate can qualify the observation. Whole-chain revocation and disabled MD2/MD4 settings remain the existing policy; no cache-only bypass, SHA1 fallback or relaxed publisher names are introduced. Signer inspection occurs before WinTrust state closure. All buffers/contexts retain their distinct owners through their required native lifetimes; cleanup uncertainty cannot yield an Available observation.

The fixed result exposes only state/stage/reason, bounded catalog/member/match counts, distinct actual Win32 and trust results, and Limited=true. It contains no paths, member tags, hashes, versions, subject GUIDs, certificate details or provider messages. The production diagnostic additionally retains attempted trust route and separate actual file/catalog results; a catalog zero does not overwrite the earlier file0x800B0100. NativeTrustResult is the most recent actual verification result, not a claim that an uncalled API succeeded. Synchronous native calls may block: an interrupted caller does not abort the worker or release its handles early. Pending work prevents another observer from starting. ReadHeld restores the caller cursor on every path; failed restoration cannot qualify trust. Uncertain catalog cleanup blocks later attempts for the process lifetime. Direct-file close failure likewise refuses fallback and later file verification, with verification and close results recorded separately. A returned unsuccessful close is cleanup uncertainty, not a claim that a native call is still running.

## Sources and validation boundary

Official Microsoft documentation and current SDK headers were checked before implementation:

- [CryptCATAdminAcquireContext2](https://learn.microsoft.com/windows/win32/api/mscat/nf-mscat-cryptcatadminacquirecontext2) and [CryptCATAdminCalcHashFromFileHandle2](https://learn.microsoft.com/windows/win32/api/mscat/nf-mscat-cryptcatadmincalchashfromfilehandle2)
- [CryptCATAdminEnumCatalogFromHash](https://learn.microsoft.com/windows/win32/api/mscat/nf-mscat-cryptcatadminenumcatalogfromhash) and [CryptCATCatalogInfoFromContext](https://learn.microsoft.com/windows/win32/api/mscat/nf-mscat-cryptcatcataloginfofromcontext)
- [CryptCATOpen](https://learn.microsoft.com/windows/win32/api/mscat/nf-mscat-cryptcatopen), [CryptCATEnumerateMember](https://learn.microsoft.com/windows/win32/api/mscat/nf-mscat-cryptcatenumeratemember) and [CRYPTCATMEMBER](https://learn.microsoft.com/windows/win32/api/mscat/ns-mscat-cryptcatmember)
- [CryptSIPRetrieveSubjectGuid](https://learn.microsoft.com/windows/win32/api/mssip/nf-mssip-cryptsipretrievesubjectguid), [SIP_INDIRECT_DATA](https://learn.microsoft.com/windows/win32/api/mssip/ns-mssip-sip_indirect_data) and [WINTRUST_CATALOG_INFO](https://learn.microsoft.com/windows/win32/api/wintrust/ns-wintrust-wintrust_catalog_info)

The separate native fixture requests only these fixed read-only observations on the disposable CI host. Its worker has a bounded caller wait, retains resources after timeout and does not start a second observation while the first remains pending. Pre-cancellation and bounded schema are checked; no fixture result is injected into the UI or production acceptance. The separate held-stream fixture checks original position seven, the same still-open SafeFileHandle and pre-cancellation preservation. The real provider identity fixture must independently demonstrate actual route lineage, strict embedded metadata and closed-gate genuine requests. The compile-only SDK probe and managed layout checks cover the supported64-bit structures. Compilation is not catalog runtime proof. Actual source-bound results, including failures or inconclusive outcomes, belong in [the execution ledger](ROADMAP-STATUS.md).

Even a successful catalog observation would establish only this selected binding on that runner, under that native policy. It would not retroactively establish why the previous file route returned0x800B0100, authenticate every Windows file or make D2/D3 checks/repairs ready. The held-stream integration has separate source-bound validation; no configuration or test switch bypasses trust or enables command execution.
