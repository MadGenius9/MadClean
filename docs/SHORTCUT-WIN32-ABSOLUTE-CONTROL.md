# Owned Win32 absolute-name rename control

`shortcut-rename-win32-absolute-control` is a separately selected development experiment in the existing marked Windows smoke fixture. It uses a fresh generated shortcut, not a personal shortcut. Production `CanMove` remains false. The earlier relative managed Win32, C++ Win32, NT and NT guard-profile checks keep their own observations; this control is neither an automatic retry nor a fallback.

The managed `ManagedWin32AbsoluteControl` backend uses `SetFileInformationByHandle(FileRenameInfo)` with `ReplaceIfExists = FALSE`, `RootDirectory = NULL`, and a full DOS destination name. Microsoft documents both fully qualified names with a NULL root and relative names with a directory root; earlier `ERROR_INVALID_PARAMETER` observations do not establish which condition caused the failure:

- [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info)
- [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle)

The only accepted destination comes from the actual final path of the matching held fixture `child` or `vault` directory handle plus the generated bounded ASCII `.lnk` leaf. The directory identity, directory/reparse/delete state, final path and source/destination volume are checked. Canonical full drive-letter paths must preserve the exact parent/leaf relation, contain safe Unicode, and remain below 1,024 UTF-16 characters. No caller-supplied arbitrary destination, UNC path, alternate stream, shell operation, overwrite, elevation or third-party executor is introduced.

The x64 counted-name buffer is zero initialized, with root at offset 8, name byte count at offset 16 and UTF-16 payload at offset 20. Before each native call the actual packed buffer must have a NULL root, a zero replacement flag, the expected byte count and exact bounded name bytes. The parent remains held through the call and is checked again afterwards. `NullRootObserved` and `AbsoluteNameValidated` describe those actual validations; `HeldDestinationParentValidated` describes the independent parent checks. `ScalarDiagRootDirValid` is null, displayed as not applicable, because this call passes no directory handle as its native root. A held parent check must not be reported as evidence of a non-NULL native root.

A positive check requires three actual calls: move, restore, and a refused no-overwrite collision. All existing source identity/link-count/byte checks, shortcut target identity/byte checks, attribute-anchor handoff, ancestor leases, teardown and no-pending-worker checks also apply. Failed or incomplete evidence remains Failed or Unknown. Reported paths, identities and content are not exported; only bounded enum/boolean/count/error facts are recorded. This backend emits no second mapped-write witness check.

The existing STA worker remains the sole native owner. Caller cancellation or the 45-second wait deadline cannot close its handles or remove its marked tree. A later control starts only after prior teardown and no pending native worker are established. Uncertain ownership retains the entire fixture tree.

This experiment does not establish namespace-race immunity, effective access, private ownership, inactivity, durable recovery, safe deletion or a production action prerequisite. A successful absolute-name control would not explain earlier relative-name failures or promote another backend's result. Linux inspection/compilation cannot establish actual Windows rename behavior; source-bound Windows observations are still required. No Windows native query or rename ran while adding this control in the cloud workspace. The local solution build does not establish Windows behavior.
