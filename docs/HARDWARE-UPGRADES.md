# Hardware Upgrades: H1 inventory and later roadmap

**H1 is the implemented read-only Hardware Upgrades inventory increment; H2 official compatibility/specification verification and H3 recommendations remain queued.** The tab runs only on an explicit user hardware-inventory action and shows allowlisted local CIM facts with their source and query-attempt time. Windows execution/rendering remains **unverified in the Linux cloud**; implementation, compilation and portable parsing tests must not be described as a successful Windows hardware query.

The tab is not a compatibility engine. It does not inspect the user's PC during development, run diagnostics/stress tests, contact manufacturers automatically, download firmware, recommend purchases, install hardware or update BIOS. Existing read-only phase-one boundaries remain in effect. Separate BIOS identity reporting supplies firmware-reported observations, not upgrade limits or compatibility proof.

## Evidence shown to the user

Every displayed claim must have one of these explicit labels. They are not interchangeable confidence levels:

| Label | Required evidence and meaning |
| --- | --- |
| **Detected / firmware-reported** | A successfully parsed local Windows provider observation, with provider/class/property, query-attempt time and coverage. An attempt timestamp is not proof that a class completed or that all its values were obtained. It reports what Windows/firmware says, which can be incomplete or incorrect. It does not prove manufacturer-supported upgrades. |
| **Manufacturer-verified** | A directly consulted official support/specification document for the exact OEM system configuration or exact retail motherboard model **and hardware revision**, with the applicable CPU/configuration/BIOS qualifications recorded. Verification is scoped to the cited claim, not the whole PC. |
| **Manual check required** | A specific physical/configuration fact that inventory and the available official documents cannot establish. Describe the required check; do not fill it with an estimate or mark a candidate compatible. |
| **Unknown / unavailable / failed / unsupported** | Missing, placeholder, conflicting, stale, inaccessible, unparsed or unsupported evidence, with the appropriate reason. An empty result does not mean an absent component, an unused slot, or compatibility. |

Keep observations and verification separate: `reported memory-array maximum` must never be relabeled `supported RAM maximum`. Preserve the source value and unit, a normalized display value only when valid, collection/retrieval time, document revision/publication date where available, and the remaining uncertainty. Do not collapse the results into a hardware-health score or a promise of performance gains.

Each later verification record must include the issuer, canonical official URL, document title/revision or support-table row, exact matching system/board/CPU identifiers, relevant configuration and BIOS branch, the specific supported claim, retrieval time, and any unresolved condition. A content hash or archived citation may help detect source changes; neither establishes authenticity without the official origin. Manufacturer source changes, identity/configuration changes or ambiguous dates invalidate the affected verification until rechecked. A recent retrieval time alone does not establish that an old document is current.

Do not automatically upload serial numbers, service tags, UUIDs, device-instance identifiers or an inventory fingerprint to a support site. Prefer model/SKU information without unique identifiers. If exact matching later requires a service identifier, use a separately reviewed, explicit user action and minimize what is disclosed. Ordinary activity logs retain operation metadata only; they must not become a hardware-identifier or browsing-history log.

## H1 — bounded local inventory

H1 implements explicit user-triggered local inventory of **exactly six classes** in `root/cimv2`: `Win32_ComputerSystem`, `Win32_BaseBoard`, `Win32_Processor`, `Win32_PhysicalMemory`, `Win32_VideoController` and `Win32_DiskDrive`. It uses fixed read-only queries and property allowlists; it does not enumerate every class property. Serial numbers, UUIDs and service tags are not requested. No automatic startup query, remote-machine query, manufacturer request or mutation method is part of H1.

The Hardware Upgrades view presents source-qualified firmware/provider-reported values and the explicit query attempt. Missing, placeholder, malformed, unavailable and partial data retain uncertainty rather than becoming compatibility conclusions. Provider metadata can be inaccurate: a board `Version` is a reported value with its hardware revision **unverified**; memory/storage byte values are logical/provider-reported observations, not measured physical allocation or available upgrade capacity. Do not sum them into free memory, free storage bays or physical availability claims.

The query follows the application's timeout, output-bound, cancellation, partial-result and metadata-only activity-log policies. Each class has at most **128 accepted records**; the query requests up to 129 to detect truncation. Failed, missing, empty, truncated or malformed class results retain their coverage limitations. The shared UI timestamp records the overall **query attempt**, not an individual provider completion time. Positive byte values remain invariant UInt64 provider-reported quantities; positive clocks/counts use bounded UInt32 values. Memory-type/form-factor codes remain raw provider enums, not manufacturer-verified compatibility claims. SMBIOS memory-type meanings are not decoded in this increment: the raw code remains visible with Unknown meaning and contributes Partial coverage even when its numeric value parsed successfully.

H1 never loads a downloaded agent, runs stress tests or infers component health from enumeration success. Portable fixtures validate contracts only and must not replace production Windows data or establish live Windows behavior.

A product UUID is not required. |
| Baseboard | [Win32_BaseBoard](https://learn.microsoft.com/windows/win32/cimwin32prov/win32-baseboard) ([source](https://github.com/MicrosoftDocs/win32/blob/docs/desktop-src/CIMWin32Prov/win32-baseboard.md)): Manufacturer, Product, Version. | The reported Version is not necessarily a usable retail PCB revision. MemoryDevices and enumerated modules must not be subtracted to claim free physical slots. Soldered memory, firmware omissions and other array layouts require exact documentation/manual checks. |

H1 acceptance and validation gates:

- Independently review the projected fields, fixed local namespace and provider permissions. Show the query-attempt timestamp, source and partial/unavailable errors without silent elevation; never present an attempt as a successful complete query.
- Bound returned objects/strings and numeric conversions. Reject malformed or unrepresentable values; do not turn zero/overflow/placeholder values into known specifications.
- Test absent/multiple boards, OEM placeholders, virtual devices, missing/unknown raw enums, large/overflowing capacity values, per-class limits, permission denial, unsupported providers and cancellation. Unexpected properties such as serials/UUIDs/AdapterRAM must not be admitted into displayed fields. Completing a provider call does not prove complete hardware coverage or reveal soldered-memory upgradeability.
- Run actual unelevated Windows runtime comparisons on disposable OEM and retail test systems before claiming Windows behavior verified. Linux parser tests and compilation alone do not pass this gate.
- The inventory screen must work without compatibility or shopping claims and without reaching manufacturer/retailer sites automatically. No release may call H1 a working upgrade recommendation engine.

## H2 — exact-model official verification

**Queued, not implemented.** H2 would add narrowly scoped, user-requested official specification/support references. It must not silently turn detected strings into search results that are labeled verified. Manufacturer sites and support documents can be unavailable, changed, regional or conditional; failed matching/retrieval remains Unknown.

**OEM machines:** use the computer manufacturer's exact system model, SKU/submodel and applicable service/configuration documentation. OEM board identifiers can resemble a retail product while using different wiring, firmware, limits or supported CPUs. OEM specifications, CPU support and **OEM firmware** govern that system; a similarly named retail board or retail BIOS is not a substitute. If the exact OEM configuration cannot be established, stop verification rather than selecting the closest retail match.

**Retail/custom systems:** require the motherboard manufacturer, exact model and hardware/PCB revision. If firmware metadata does not establish the revision, ask for a safe manual identification from official documentation/board labeling before selecting a revision-specific support list. A shared socket, chipset, product-family name or visual resemblance is insufficient. Conflicting or incomplete official evidence blocks the affected claim; lack of an item on a memory qualification list is not proof that it is incompatible, and the existence of a qualification list is not proof that an unlisted kit is supported.

Official manufacturer source entry points include [ASUS CPU/memory support-list guidance](https://www.asus.com/support/faq/1043883/) and [Lenovo Product Specifications Reference](https://psref.lenovo.com/). The cloud proxy denied their direct HTTP reads (403), so their current contents and any device-specific limits are **unverified here**. They are source-selection examples, not recommendations or verified specifications for the user's PC. H2 must directly retrieve the appropriate current official OEM/board support document and model-specific tables before making any manufacturer-verified claim; these links and this roadmap do not satisfy that gate.

| Topic | Evidence required before marking the particular specification verified | Unresolved checks that must stay visible |
| --- | --- | --- |
| RAM types and maximums | Exact OEM/board/revision documentation; supported DDR generation, DIMM/SO-DIMM or soldered arrangement, buffered/registered/ECC qualifications, per-module and total limits, density/rank/channel/population rules, relevant CPU memory-controller limits and any BIOS prerequisites. Distinguish supported JEDEC operation from optional XMP/EXPO/other overclock profiles. | A firmware array maximum is not the supported limit. Do not derive “free slots,” replaceable modules or soldered-RAM upgradeability from WMI counts/form-factor flags. If the official design or installed configuration is unresolved, require manual checks. Never enable memory profiles automatically. |
| CPU support and required BIOS | Exact CPU SKU/variant/stepping where the vendor distinguishes them, exact board revision/OEM configuration, official CPU support-table entry and its required BIOS branch/minimum version, plus power/thermal/support qualifications. Compare installed BIOS identity only through the relevant vendor's version rules. | Socket alone does not prove compatibility. Similar CPU names are not interchangeable. Missing/ambiguous firmware versions, required intermediate firmware, platform limitations or a support-table mismatch leave compatibility pending. A BIOS prerequisite does not authorize flashing. |
| Expansion and GPU options | Exact board/OEM slot and lane-sharing documentation, supported CPU-dependent lane configurations, slot electrical/physical requirements and the candidate's official interface/power/dimension specifications. | **Never infer PSU capacity/connectors, case/GPU clearance, free physical slots or usable slot spacing.** Require actual PSU/model/connector and physical fit/obstruction checks; do not assume the OEM's optional larger PSU or larger chassis was installed. Cooling, power delivery and display requirements can remain blockers. |
| Storage options | Exact supported socket/bay/port documentation, M.2 key/length and SATA-versus-PCIe/NVMe protocol, CPU/chipset lane-sharing or port-disable conditions, and relevant OEM limitations. | Installed disk counts do not establish free bays/ports or supplied cables/brackets. Physical occupancy, mounting space, cooling, controller/RAID configuration and data-migration/encryption considerations require independent review. No disk action is authorized by discovery. |

A Windows Update firmware offer describes an update package and applicability under that service. Its package/driver version is **not automatically the installed BIOS version**, a vendor support-table version or proof of a compatible CPU upgrade. Keep those sources/version namespaces separate. Do not derive “BIOS current” from no Windows Update offers. H2 has no firmware download, updater launch, installation, firmware-setting change or restart action.

H2 acceptance gates:

- Reject fuzzy model/revision matches and OEM-to-retail substitution. Record the exact source row and applicable hardware/CPU/firmware constraints for every verified limit; failed retrieval, unresolved conflicts and missing qualifications remain Unknown.
- Test generic/ambiguous OEM identities, similar model names/revisions, missing/obsolete/contradictory support pages, unsupported CPU variants, conditional RAM maxima, vendor-specific BIOS version strings and source timestamps. Fixture documents must be visibly test data, never production verification.
- Independent review must confirm that detected, manufacturer-verified and manual-check information stay distinct. Static citation presence alone does not pass compatibility verification.
- Restrict any future retrieval to reviewed official origins and bounded safe document handling. No arbitrary model-string URL execution, downloaded programs, firmware assets, support-site sign-in, serial upload or retailer scraping is enabled by H2.

## H3 — bounded advisory recommendations

**Queued, not implemented.** H3 starts only after H1/H2 and their runtime/review gates pass. Before recommending products or capacity/price tiers, obtain the user's **budget and currency/region, intended use cases/workloads, current bottleneck or objective, and relevant constraints** such as noise/power/space, reliability, warranty or keeping existing parts. Do not infer these preferences from inventory. Missing preferences permit inventory and unresolved-check explanations, not personalized purchase recommendations.

A later recommendation must name the exact candidate/kit/variant, intended benefit for the stated use case without unsupported benchmark promises, compatibility evidence and its time/scope, additional parts/costs where known, and all manual verification still required. Prices/availability require a dated, separately authorized source; no current pricing or product recommendation is supplied by this document. Do not suggest that replacing hardware is necessary merely because it is old or because a newer part exists.

H3 acceptance gates:

- Each candidate must satisfy the applicable OEM/board revision, CPU support/required BIOS, memory type/capacity/population, interface/lane-sharing, power/cooling and physical-fit constraints. Any required constraint without evidence prevents an action-ready “compatible” result; label a conditional candidate as pending verification instead.
- Present verified limits separately from advisory choices, with alternative/no-change paths and clear user preferences. Surface uncertainty and conflicts without a scalar compatibility percentage.
- Independent tests/review must cover missing budget/use case, unknown PSU/clearance/occupancy/soldered design, ambiguous BIOS prerequisites, conflicting sources and stale verification. No fully approved recommendation may escape when a required physical or manufacturer check is unresolved.
- The user must review compatibility and any firmware prerequisite before a later selected action. This roadmap authorizes **no purchases, cart actions, component installation, BIOS/firmware downloads or updates, forced restarts or silent elevation**. Such capabilities require a separate explicit request and safety review; restore points are not hardware compatibility evidence or a recovery guarantee for firmware changes.
