# Selected shortcut file evidence

Shortcut review now offers a separate **Inspect selected file evidence** action. It reads one selected `.lnk` file's bounded contents and current supported target metadata. Ordinary inspection and the existing metadata-only selected recheck do not invoke it. No shortcut or target is moved, saved, resolved, launched or removed.

The selection comes from the exact source inventory row and chosen folder. A changed selection, folder or inventory invalidates the displayed result; late results from an earlier selection are discarded. The original inventory remains historical. It did not record a full native identity, so matching a fresh path cannot establish continuity with the original file object.

The Windows provider checks configured protected folders, including actual user/common Startup folders, before reading contents or invoking Shell metadata. Unknown or unsupported exclusion locations block the read. The provider then uses fresh fixed-local, no-follow ancestry guards and a bounded read handle for the exact file. It observes full 128-bit file identity, volume, size and link count, reads at most 1 MiB, and compares byte fingerprints and metadata around the existing read-only Shell/target query. Multiple hard links, unsupported or changing metadata, invalid times and unavailable access cannot produce a documentary preview.

These checks describe observations during this read. Sharing access and repeated fingerprints do not establish inactivity, immutable contents, application ownership or future path stability. All handles close before publication. DACL and effective permissions are **Not checked**; no private-file or quarantine claim is made. Protected-folder coverage does not prove that an arbitrary custom application folder is outside the selected scope.

The portable policy requires source/time/path consistency and fresh bounded evidence. A current supported missing target can produce a documentary preview; a restored target blocks that review. Network/offline/ambiguous/unreadable target evidence stays unknown. Partial inventory or current metadata coverage remains Partial. Missing is evidence at a point in time, never proof that a shortcut is obsolete.

`CanMove` is a get-only constant false. There is no move handler, configuration bypass, deletion API or action token. Full native identifiers and byte fingerprints stay in memory and are omitted from the UI summary and activity log. The activity log records only the fixed `ShortcutFileEvidence` area, outcome and time.

The development fixture exercises only owned links and targets on the disposable Windows runner. It checks actual identity/hash facts, a target appearing between reads, hard links, cancellation and unchanged files. It exports only bounded states/counts/booleans. Pending metadata retains its worker resources and the entire fixture tree; the caller never forces disposal or deletion beneath the worker.

Independent combined review found no remaining material blocker after correcting historical Partial coverage overriding an unknown/blocked current read. Genuine current failure states stay distinct. This skips existence verification, not a blanket promise about all underlying OS behavior. Unsupported redirected exclusion paths block the content read.
