# Startup registry binding research — 2026-10-27

**Research only. The production and fixture mutation methods remain unavailable. No registry operations, native experiments, executor changes or builds were performed for this research.** Current official Microsoft pages were freshly retrieved with HTTP 200 except the explicitly noted missing Win32 reference pages.

The public Win32 contract provides a more promising handle-relative route than the original unresolved gate implied. Missing `REG_OPTION_OPEN_LINK` in `RegOpenKeyTransacted` alone does **not** establish that safe enlistment is impossible. However, these references do not by themselves prove the entire no-follow/ancestor/rename/concurrent-writer and durable-recovery contract required by MadClean. Canonical names and equal value bytes are insufficient substitutes for that proof. Do not enable an executor on the strength of this document.

## What the Win32 contract actually says

[RegOpenKeyTransactedW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regopenkeytransactedw) accepts an `hKey` returned by `RegOpenKeyEx` as well as transacted opens. Its optional `lpSubKey` can be NULL or an empty string. For a predefined key this refreshes/returns the same predefined handle; otherwise the documentation says **“phkResult receives a new handle to the opened key.”** It also states that opening associates the key with the supplied transaction and that subsequent operations on the returned key are transacted. This is a documented ordinary-handle-to-transacted-handle entry point, not an undocumented function or an option-bit workaround.

The same page requires `ulOptions = 0` and the extended parameter NULL. It explicitly excludes a returned predefined key from the transaction, says subkeys are not automatically transacted, and requires reopening with an active transaction after commit/rollback. Its interference rule says a non-transacted operation on the key before commit rolls the transaction back. A design must use returned enlisted handles for every intended key and journal operation; holding an ordinary ancestor handle does not automatically enlist the subtree. Do not translate that rule into an undocumented guarantee about every ancestor rename, link retarget or unrelated namespace operation.

[RegOpenKeyExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regopenkeyexw) separately documents `REG_OPTION_OPEN_LINK`. A future experiment could start with individually opened no-follow components, reject links, then use non-predefined handles and NULL/empty subkeys for documented enlistment. The transacted-open page does not explicitly specify the corner case of reopening an already-open symbolic-link key handle, whether link lookup is repeated, or how this relates to concurrent ancestor renames. These are specific remaining proof obligations; they are not evidence that the ordinary-handle overload is unsupported.

## Native key names do not supply object identity

The current [ZwQueryKey documentation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-zwquerykey) explicitly states: **“If the call to this function occurs in user mode, you should use the name ‘NtQueryKey’ instead of ‘ZwQueryKey’.”** Calling the native query from user mode is therefore discussed by Microsoft; describing it as entirely undocumented would be inaccurate. The page's requirements table is nevertheless a WDK/kernel reference (`wdm.h`, `NtosKrnl.lib`, `NtosKrnl.exe`). The attempted separate Win32 `winternl/NtQueryKey` reference URL returned 404; a missing page is not proof that an export is absent.

[KEY_INFORMATION_CLASS](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ne-wdm-_key_information_class) defines `KeyNameInformation`. [KEY_NAME_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_key_name_information) promises a name and byte length, with a non-NUL-terminated character array. It does **not** promise a stable unique key identifier, lock, atomic pathname verification, a canonicalization algorithm or transaction-isolation semantics for the name query. `KeyFlagsInformation` and `KeyHandleTagsInformation` are explicitly reserved for system use; they are not supported substitutes for a public link-type/identity interface.

A name observed through a handle can be useful scope evidence. It must not be relabeled an immutable object identity. [RegRenameKey](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regrenamekey) can rename the key identified by a handle with NULL `lpSubKeyName`; ordinary handle retention is not documented as a rename-denial mechanism. A prior name can subsequently refer to another object. Comparing a name before/after an operation leaves a race unless the relevant namespace stability follows from the actual transaction contract. Equal value kind/bytes can also describe another registration or a same-value delete/recreate sequence; equality is not proof of uninterrupted identity or application authorship. It remains necessary to decide precisely whether the selected action is bound to an object, a path-defined registration, or both. MadClean's present gate must not silently weaken that requirement.

[RegDeleteKeyW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regdeletekeyw) says a deleted key is not removed until its last handle closes. This supports retaining handles, but does not establish that names can never change or that all namespace races disappear. [RegCreateKeyExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regcreatekeyexw) documents link creation with `REG_OPTION_CREATE_LINK` and the absolute target stored in `SymbolicLinkValue`. The consulted Win32 references do not explicitly establish a general immutable link/ordinary-key-type theorem under all supported actors. Do not infer that theorem merely from a currently absent link value or from successful fixture observations.

[CompareObjectHandles](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-compareobjecthandles) compares kernel-object handles. Its general promise does not establish that separate registry opens necessarily expose the same kernel object for the required registry key identity. No such assumption is needed to quote the documented NULL-subkey overload, and an unexplained false comparison must not trigger a path-based fallback.

## Another native route exists, with a different support question

[ZwOpenKeyTransactedEx](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-zwopenkeytransactedex) explicitly offers `REG_OPTION_OPEN_LINK` **and** transaction association, on Windows 7 and later. Therefore the absence of this option in the Win32 wrapper is not absence of such an operation in Windows. The page describes kernel callers and `NtosKrnl` requirements; unlike `ZwQueryKey`, it does not specifically give a user-mode `NtOpenKeyTransactedEx` calling contract. [Using Nt and Zw versions](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/using-nt-and-zw-versions-of-the-native-system-services-routines) explains user-mode argument semantics in general, but does not supply every routine's desktop ABI/support guarantee. The attempted dedicated Win32 `NtOpenKeyTransactedEx` reference URL returned 404.

This is a research lead, not authorization to P/Invoke an assumed signature or load an undocumented syscall. Microsoft also cautions in [Calling Internal APIs](https://learn.microsoft.com/en-us/windows/win32/devnotes/calling-internal-apis) that internal `Winternl.h` interfaces can change and recommends equivalent public functions. That general warning is not a claim that every documented Nt routine is unsupported; it is a reason to distinguish the specific explicit user-mode query guidance from a kernel-only transacted-open reference.

## Remaining gate and possible bounded follow-up

The next supported investigation should prioritize the public `RegOpenKeyTransacted(non-predefined existing handle, NULL, ...)` contract rather than asserting the wrapper cannot do it. Before any implementation, independently review the meaning of “opened key” for an ordinary no-follow source handle, component/link-type validation and all required ancestor bindings. Confirm what documented transaction interference covers for rename, delete/recreate and link retarget, and define whether same-value concurrent replacement must be rejected. A canonical-name comparison may supplement that analysis; it cannot replace it.

Only then could a separately authorized native fixture under MadClean's owned test subtree test ordinary-source enlistment, direct/ancestor link rejection, rename/source replacement, equal-value races, transaction abort/commit observation and fail-closed unavailable APIs. Tests would verify behavior on the tested Windows build, not create an otherwise missing supported-contract guarantee. Backup privacy, filesystem durability/read-back, registry-journal atomicity, restore-when-absent, stale one-shot previews and uncertain-commit handling remain separate gates even if binding is resolved. No cross-resource filesystem/registry atomicity or automatic recovery is implied. The Windows Settings handoff remains the implemented supported management route.
